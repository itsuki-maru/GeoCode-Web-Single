# PC UI 仕様

## 1. 概要

PC用のVueアプリ。地図オブジェクト一覧、レイヤ、画像・動画・PDF、アカウント、共有、印刷の操作を提供する。地図本体はバックエンドの `/map` をiframeで表示する。

関連: [全体構成](../SPECIFICATION.md)、[モバイル](../frontend-mobile/SPECIFICATION.md)、[地図スクリプト](../template-scripts/SPECIFICATION.md)、[機能・API仕様](../../SPECIFICATION.md)。

## 2. ディレクトリ構成

```text
frontend/
├── index.html                  ViteのHTML入口
├── public/                     アイコン・manifest・地図共通CSS等
├── scripts/                    vendor配置、印刷PDF確認
├── src/
│   ├── main.ts / App.vue        起動・アプリ枠
│   ├── router/                 画面遷移、API URL定義
│   ├── views/                  トップ・地図・認証画面
│   ├── components/             機能別UI部品
│   ├── stores/                 Piniaのアプリ状態・API操作
│   ├── composables/            画像処理、選択レイヤ、表示状態等
│   ├── assets/                 ソースから参照するスタイル等
│   ├── axiosClient.ts          Cookie付きAPI通信・認証更新
│   ├── interface.ts            UI側データ型
│   ├── setting.ts              Vite環境変数の参照
│   └── test/                   テスト共通設定
├── tests/template-js/          地図・Teraとの接続テスト
└── dist/                       個別ビルド成果物（生成物）
```

`src/**/__tests__/` は対象実装に対応するテスト。ディレクトリ内のメモや雛形ファイルの存在は、画面から利用されていることを意味しない。参照元はrouter・views・importで確認する。

## 3. 起動と画面遷移

[main.ts](src/main.ts) はPiniaとRouterを登録し、`appInits.init()` の完了後にマウントする。現実装は `finally` 内でもinitを呼び出すため、初期設定取得を再度開始する。`App.vue` が地図画面へ遷移させる。

| Vue内パス         | 画面                  | 処理                                           |
| ----------------- | --------------------- | ---------------------------------------------- |
| `/`               | `AppTop.vue`          | トップ用ルート                                 |
| `/mapview`        | `MapView.vue`         | 認証確認後、マーカー・レイヤ・画像の取得を開始 |
| `/account/login`  | `auth/LoginView.vue`  | ログイン・TOTP認証                             |
| `/account/signup` | `auth/SignupView.vue` | アカウント登録                                 |

地図ルートは `/account/auth` の失敗時にloginへ遷移する。ルートガード内の各 `initList()` は呼び出し後に待機せず遷移を進めるため、一覧取得完了を保証するガードではない。図形の取得は地図画面側でも行う。

`/app-init` の `app_title`、`allow_user_account_create`、`allow_user_update_password`、`allow_origins` をUI設定として使用する。実際の操作可否はバックエンドでも検証される。

Service Workerはload時に登録する。`public/service-worker.js` に特別なfetchキャッシュ処理はなく、オフライン地図機能を提供するものではない。

## 4. 画面と主要機能

地図画面の連携をまとめる実装は [MapView.vue](src/views/MapView.vue)。

| 配置                                | 主な責務                                                       |
| ----------------------------------- | -------------------------------------------------------------- |
| `components/map/`                   | ツールバー、地図iframe、全画面表示、印刷モーダル               |
| `components/map-object/`            | マーカー・図形の統合一覧、詳細編集、公開入力フォーム設定       |
| `components/layer/`                 | レイヤ作成・一覧・改名、マーカーアイコン、重ね合わせタイル選択 |
| `components/image/`                 | ファイル一覧、アップロード、プレビュー                         |
| `components/share/`                 | 一時共有URLの設定・発行・表示                                  |
| `components/qrcode/`                | QRコード表示                                                   |
| `components/location/`              | 現在位置共有セッションの制御                                   |
| `components/json/`                  | JSONインポート用UI                                             |
| `components/site/`                  | 外部サイトURL設定                                              |
| `components/UserPrivacySetting.vue` | プライバシー、パスワード、TOTP等のアカウント設定               |
| `components/common/`                | 確認・通知・進捗・モーダル枠                                   |

地図の図形描画・計測・検索はiframe側で実装する。一覧からの選択や編集結果はiframeへ通知する。印刷は `/map-another?print=1` の専用iframeを使用し、現在の地図状態と対象レイヤを引き渡す。

### PCとモバイルの主な差

| 項目                         | PC                              | モバイル                          |
| ---------------------------- | ------------------------------- | --------------------------------- |
| Vue入口                      | `main.ts` / `App.vue`           | `mainMobile.ts` / `AppMobile.vue` |
| 地図高さ                     | MapIframeのheightをvhとして適用 | MapIframeは100vh                  |
| 印刷モーダル                 | あり                            | 対応コンポーネントなし            |
| JSONインポート専用モーダル   | あり                            | 対応コンポーネントなし            |
| 外部サイト設定コンポーネント | あり                            | 対応コンポーネントなし            |
| 一覧開閉の永続化composable   | あり                            | 対応composableなし                |
| 編集地図                     | PC用profile                     | タップ向けprofile                 |

これは現行ソースの実装差であり、バックエンドAPIの可否を表す表ではない。

### JSON取り込みと成功後の同期

- JSON形式・容量制限は従来どおり。PCの取り込みPOSTには操作ごとのUUIDを `Idempotency-Key` ヘッダで付ける。401の認証更新・通信失敗後の再送は同じキーを維持する。
- 未解決の操作をアカウント（masterレイヤのuser_id）とJSONファイルのSHA-256に対応付け、sessionStorageへメタデータだけを保存する。モーダル開閉・選択変更・同一タブの再読み込みでも同じ要求を復元し、API成功後の意図的な再取り込みでは新しいキーを作る。HTTP環境でも動作し、JSONの数値をJavaScriptの数値へ変換しない。
- 送信前に認証中の利用者を確認し、`X-Import-Account` に期待するuser_idを指定する。別タブなどでアカウントが変わっていれば送信を止める。確認後に切り替わった場合もAPIが登録前に不一致を拒否する。
- `JsonImportModal` はPOST成功を親へ通知する。ストアと地図の更新は `MapView` が担当し、レイヤ一覧と既存の選択レイヤ同期処理を使ってマーカー・図形を再取得し、同一URLでもiframeを強制再読み込みする。選択レイヤを維持し、検索条件を解除する。
- API送信中・画面同期中・iframe読込中の進捗を分け、子の送信終了通知が親の同期中表示を消さないようにする。画面同期だけの失敗は「インポートは完了したが画面更新に失敗」と案内し、再試行はGETと地図更新だけを行う。

## 5. 状態管理

| ストア        | 責務・取得元                                          |
| ------------- | ----------------------------------------------------- |
| `appInits`    | `/app-init` のアプリ設定                              |
| `auth`        | UI認証状態、再認証中・トークン更新中フラグ            |
| `layers`      | `/layer/read/all`、レイヤ更新・削除                   |
| `mapobjects`  | マーカーMap、統合検索結果の図形ID、マーカー更新・削除 |
| `shapes`      | `/shapes` の図形Map、名前・レイヤ・GeoJSON更新        |
| `images`      | 初期50件・検索50件のファイル一覧                      |
| `markerIcons` | マーカーアイコンの取得・検索等                        |

Piniaの内容はAPIデータをUIで扱うためのメモリ上の状態であり、DBの代わりではない。統合検索は `/map-objects/read/query` の `markers` と `shape_ids` を使う。データ更新後は、操作に応じてストア更新、再取得、iframeの部分更新・再読み込みを行う。

### ブラウザ保存

- `geocode-web:last-active-layer-id`: 最後の選択レイヤ。現在利用できる一覧に存在しなければmasterへ戻す。
- `geocode-web:map-object-table-open`: 一覧の開閉。未設定時は開く。
- `loginuser` / `loginUser`: ログイン画面が保持するユーザー関連値。大文字小文字の異なるキーが存在する。
- 地図の中心・表示設定・タイルの状態は [地図スクリプト仕様](../template-scripts/SPECIFICATION.md) を参照。

選択レイヤ・一覧開閉キーにアカウントIDは含まれない。ログイン状態の最終判断はAPIで行う。

## 6. API・認証・iframe連携

[router/urls.ts](src/router/urls.ts) が主なAPI URLを定義する。一部コンポーネントはURLを直接組み立てるため、定数一覧だけをAPI利用一覧としない。

[axiosClient.ts](src/axiosClient.ts) は `withCredentials: true` を設定する。FormDataの場合はContent-Typeを削除してブラウザにboundary設定を任せ、その他はJSONとする。

401の `token_expired` は `/account/refresh` を呼び、並行リクエストで更新Promiseを共有して元の要求を再試行する。更新失敗・`refresh_token_expired` はログアウト状態にしてログインへ遷移する。再認証・トークン切り替え中は先行遷移を抑止する。すべての401を同じエラーとして扱うわけではない。

[MapIframe.vue](src/components/map/MapIframe.vue) はfocus、絞り込み、更新、削除、タイル変更を送信し、画像表示・再読み込み・ログイン遷移・位置情報・印刷開始を受信する。送信先originはiframe URLから算出する。受信は許可originに加えiframeのcontentWindowとの一致を検証する。

更新要求はrequestIdで応答を対応付け、2秒でfalseを返す。地図画面側は反映できなかった場合の再読み込みを処理する。完全なメッセージ一覧と印刷通信は [スクリプト仕様](../template-scripts/SPECIFICATION.md) を参照。

## 7. 開発・配布・テスト

このディレクトリで実行する:

```sh
npm ci
npm run dev
npm run type-check
npm run test:run
npm run test:template-js
npm run build
```

`build-only` はViteビルド後に [copy-vendor-assets.mjs](scripts/copy-vendor-assets.mjs) を実行する。この処理が他の地図画面にも必要なvendor資材を供給する。`dist/` の統合・Rustへの組み込みは [全体仕様](../SPECIFICATION.md) の手順を使用する。

`src/**/__tests__/` は認証、router、ストア、composable、モーダル、iframe、位置共有などを検証する。`tests/template-js/` はtemplate-scriptsとTera、vendorをまたぐ契約・スモーク・印刷テストを含む。

印刷PDFの任意確認は `scripts/check-print-preview.mjs` と `scripts/check-print-preview-pdfs.py` を使用する。ブラウザ・Playwright・Python等の別途準備が必要で、詳細な実行例は [README](../../README.md) を参照する。

## 8. 変更時の注意

- UI型は [interface.ts](src/interface.ts)、地図型はtemplate-scripts、API型はRustに分かれている。データ変更時はそれぞれ照合する。
- iframeのメッセージ名はモバイルと一部異なる。受信側と送信側を同時に確認する。
- ルートガードは認証確認であり、各データ取得の完了・成功を一括保証しない。
- lint/formatは修正を伴うスクリプトである。閲覧・確認だけの目的で実行しない。

## 共通フォーム管理・適用

- 上部ツールバーの「共通フォーム」から `CommonFormsModal.vue` を開く。PCは `left-btn-header-zone`、モバイルは上部ツールバーに配置する。
- 「作成」「一覧」で操作を切り替え、新規作成、一覧取得、編集、保存、削除を行う。保存・削除後は一覧を更新する。読み込み失敗時は再読み込みできる。
- 項目編集は `MapObjectFormSettingsModal.vue` の共通フォームモードを再利用する。対象別フォームと同じ入力型・検証を使用し、共通フォームモードには公開URL・パスワード・公開状態の操作を表示しない。
- 対象別の「入力フォーム」ではプルダウンから共通フォームを選び、置換を確認して読み込む。保存するまで対象へ確定しない。公開状態・URL・パスワードは維持する。
- 適用元ID・版と項目IDを維持して保存する。項目の種類変更時には新しいIDを発行する。意味を変更する場合は削除・追加を案内する。
- 共通フォームの変更は既存のコピーに波及しない。削除確認で適用済みフォーム・回答履歴が残ることを説明する。
- 更新競合（409）は開き直して再編集するよう案内する。保存・適用中は編集操作を無効にし、失敗時は入力内容を保持してメッセージを表示する。
- 小さい画面では入力欄を縦配置し、モーダル内をスクロールして操作する。

- 共通フォームの入口には `form_24.png` を使用する。作成・一覧の切替はレイヤ作成と同じ `layer-type` のラジオ形式。見出し・切替・再読み込み欄はスクロール領域の外に置き、フォーム一覧だけをスクロールする。
- 共通フォームの削除・コピー適用は既存の `MessageModal` に実行ボタンを表示して確認する。閉じる・オーバーレイ操作では実行しない。
- 適用欄ではプルダウンと「共通フォームを使用する」ボタンを横並びにする。

- 共通フォーム管理の作成・一覧ラジオ間隔は32pxとし、閉じるボタンは既存モーダルと同じグレー背景のスタイルに統一する。
- 共通フォーム作成・管理ボタンは `left-btn-header-zone` の末尾に配置する。ユーザー設定ボタンは `App.vue` の `other-function-btn-zone` へ移動し、同領域のアイコンボタンスタイルで、表示中の地図画面が公開する操作から既存のプライバシー設定モーダルを開く。

## 回答履歴・最新回答・CSV（第2段階）

- `components/map-object/FormAnswersModal.vue` が回答一覧・条件検索・詳細表示・CSV出力を担当する。
- 共通フォーム管理の全件入口、各共通フォームの回答一覧、対象別入力フォームの回答履歴から開く。削除済み共通フォームも回答の検索候補へ含める。
- 履歴／最新回答を切り替え、共通フォーム・版・対象種別・対象ID・名前・レイヤ・投稿日時・型別の回答条件で検索する。回答条件は最大10件のAND。最新選択後に版・期間・回答条件を適用する。
- PCは表、700px以下はカード形式。表示項目を選択でき、詳細には投稿時の項目名・順序・値を表示する。定義なしの旧回答は項目IDで表示する。
- 検索とページ移動はサーバーで実施し、次ページは検索基準日時とカーソルを維持する。表示は50件単位。
- CSVは表示中の検索結果を全件出力する。未検索の条件編集を混ぜない。事前検証後に通常のフォーム送信でダウンロードし、JavaScriptのBlobへ全件を蓄積しない。上限は10,000回答・200項目。
- 入力日時は端末のタイムゾーンからUTCへ変換し、表示日時は端末のタイムゾーンを使用する。CSVの日時はUTCと明記する。
- 詳しい検索・旧回答・CSV列・所有権の仕様はルート `SPECIFICATION.md` の第2段階を参照する。

- 共通フォーム管理の見出しには `modal-h2` を使用する。全フォームの「フォームからの回答一覧と分析」は作成タブの作成ボタンの隣にボタンとして配置し、一覧タブは各フォームの回答一覧ボタンのみを表示する。
- 共通フォーム管理・項目編集のボタン（上下移動・項目削除を除く）は `btn-close` を付け、`form-modal-buttons.css` で既存のグレー背景ボタンと同じスタイルに統一する。確認メッセージも同じ配色とする。回答一覧のボタンもグレー背景に統一する。

### 回答一覧の操作と表示

- CSV隣の「地図で確認」は反映済みの検索条件・基準日時で全ページの対象を開く。`AnswerMapModal.vue` が `/form-answers/map` へ通常のPOSTフォームを送り、返却された閲覧専用地図をiframeに表示する。対象重複はサーバーで除去する。
- 地図は半透明の全画面オーバーレイ（z-index 100）に、余白・角丸を持つ高さ95dvhのコンテンツを重ねる。回答数／対象数は上部、閉じるボタンは画面左下へ固定する。読み込み・再試行・表示できない対象数の案内に対応する。閉じた後も一覧の状態は保持する。メッセージのorigin・source・request_idを検証する。上限・最新回答の意味・現在位置情報の扱いはルート仕様の第3段階を参照。

- 検索項目・表示項目候補（column-options）・テーブル列はフォームの入力順とする。共通フォームの新しい版または対象の現在設定を優先し、過去だけの項目は末尾に追加する。表示列のチェックを外して再選択しても入力順を維持する。

- 初期状態は検索欄を閉じ、回答を自動表示。「絞り込み」で基本条件、「詳しい条件」で版・対象種別・レイヤを開く。条件は「絞り込む」または「変更を反映」で適用し、検索欄の開閉状態を維持する。「条件を追加」「条件をクリア」「絞り込む」は横一列に配置する。未反映の変更を表示し、ページ移動・CSVには反映済みの条件を使用する。
- 対象IDは直接入力せず、対象別設定からの絞り込みを内部で維持する。条件クリアでも呼び出し元のフォーム・対象範囲は維持する。表示モードは変更しない。
- 項目名を基本表示とし、同名項目は種類と番号で区別する。UUID等は詳細の折りたたみ「管理用情報」へ移動する。定義のない旧回答は「項目名不明の項目 N」と表示する。
- PCは見出し固定の表、700px以下はカードで回答項目を先頭3件まで表示。長文・全項目は「詳細を見る」で確認する。選択肢の複数条件はチェックボックスを使用する。CSVの列・識別子・検索順序は変更しない。
- 表は地図トップと同じ濃色見出し・交互背景・ホバー色を使用し、一覧内の縦スクロール中も見出しを固定する。PC版のテーブル領域の最大高さは43dvhとする。基本条件は広い画面で4列、詳しい条件は3列。1000px以下は基本条件2列、700px以下は両方1列とする。
- 一覧・CSVの説明はCSV横の22pxの「?」で開閉する。日時の説明文とCSVダウンロード開始の成功メッセージは表示しない。回答詳細は長い文字列を折り返して横方向にはみ出さないようにする。

- 共通フォーム管理は「作成」を初期タブとする。タイトルはモーダル幅全体で中央寄せ・下線表示し、閉じるボタンは右上に配置する。作成タブの「フォームからの回答一覧と分析」は作成ボタンの隣のボタンとして表示する。背景クリックでも閉じる。
- 対象別入力フォームの回答履歴は共通フォーム適用操作と横並びに配置する。公開URLの「フォームを確認」はURLコピーと同じグレーのボタンスタイル、「URLを再発行」は青（`#1c3abe`）。項目の上下移動・削除は従来の白背景（削除は赤文字）を維持する。

- 「共通フォームの作成」「共通フォームの編集」の見出しには `modal-h2` を付けない。管理モーダルのタイトルは全幅中央・下線を維持し、狭い画面では右上の閉じるボタンとタイトルを別行に配置する。

## 回答地図の追加絞り込み

- PostgreSQL版・SQLite版共通。回答地図専用の `form-answer-map.html` / `form-answer-map.ts` を使用し、通常の `map-anather` と印刷の経路を維持する。SQLite版にも同機能を反映済み。
- PC・モバイルのAnswerMapModalは同一構成。共通フォームと最大10件のAND条件で初期対象を絞る。日付・数値の範囲は両端を含む。0・false・未入力・項目なしを区別する。値はsubmitted_values、定義はform_snapshotを使用する。
- 初期map APIから取得したquery/as_ofと対象IDをmap-filter JSON APIに渡す。候補は追加条件で狭めず、0件でも編集・解除できる。候補・件数・検索は読み取りトランザクション内で取得する。
- answer-filter.tsはorigin・親window・requestId・更新IDを確認し、初期対象の部分集合だけを受け付ける。対象IDは種別を含む。保持済みレイヤを再利用し、iframeを再読み込みしない。中心・ズーム・名前検索・レイヤ選択を保持する。
- 共通検索のisRecordAllowedは任意の判定関数。未指定の通常地図は従来動作。回答地図では検索解除・レイヤ切替でも追加条件を維持する。表示件数は実際に表示中のレイヤを数え、表示不可の対象と区別する。
- 失敗時は直前の地図を維持し、古い応答・閉じた画面の応答を破棄する。解除は元の一覧条件へ戻す。範囲変更は「表示対象に合わせる」で明示的に行う。閉じるボタンは左下。一覧状態・通常地図設定は保存変更しない。
- answer-preview.tsは初期の範囲調整・件数・query/targetsのready通知を担当する。失敗はform-answer-map-error.htmlで通知する。HTMLのJSON値はjson_encode_for_html経由とし、成功・失敗ともno-store。
- `answer-analysis.ts`と任意analysis入力は旧呼び出しの互換性維持に限って残す。現在の「地図で色分け」は別の一時状態で管理する。
- 回答地図のPC表示（幅701px以上）は絞り込みを左20%、地図を右80%に配置する。右下の開閉ボタンで絞り込み全体を隠し、地図を全幅へ広げる。開閉ではiframe・入力条件を保持する。幅700px以下は上部配置を維持し、操作ボタンを等幅2列、フォーム選択を全幅に配置する。狭い画面への切替時も絞り込みを操作可能にする。
- 回答地図のPC版ヘッダーはapp-headerと同じ黒背景・whitesmoke文字とし、モバイル版ヘッダーは従来の白系背景を維持する。

## 回答地図の色分け

- PC・モバイルの「地図上で絞り込み」と同じ階層に「地図で色分け」を配置する。1つの共通フォームに対し、分類名・色・AND条件を設定する。複数分類に一致する対象は上の分類を優先し、未分類は元のスタイルを維持する。
- 既存map-filter APIを分類ごとに利用する。一覧条件・反映済み地図条件・その分類条件を同一回答へAND適用する。query.conditionsと外側conditionsへ最大10件ずつ配分し、各分類の合計上限は20件。最新／履歴モードと基準日時を維持する。バックエンド・DBを変更しない。
- 入力中と適用済みの分類を分け、全分類の取得成功後にtargetsとcoloringを同じanswer-map-filter要求で反映する。ACK後に適用状態を確定し、失敗・古い応答では直前表示を維持する。絞り込み変更時は適用済み分類を再評価する。

- PC印刷には適用済みcoloringを任意項目として凍結転送する。色分けのない印刷には凡例設定を追加しない。凡例は分類IDごとに色と分類名を1行表示し、印刷対象のない分類は表示しない。初期値は全体表示ON・全分類ON・地図連動OFF。凡例全体の非表示は地図へ作用させない。分類の地図連動はその分類の全対象へ適用し、既存の絞り込み・検索・レイヤ表示とANDで判定する。印刷内だけに保持する。

## 回答地図・CSVの認証更新

- PostgreSQL版のPC・モバイル共通。地図初回表示・再試行とCSV実ダウンロードは、authenticated-form.tsを介してネイティブフォーム送信する。CSVをBlobへ蓄積せず、既存のストリーム出力を維持する。

- 親はorigin・iframeのcontentWindow・要求IDを検証し、apiClient経由のGET /account/authで既存のリフレッシュ・再試行処理を実行する。成功後、同じフォーム内容を最大1回だけ再送する。認証更新失敗や再送後の401はエラーを表示する。

## 回答地図の印刷（PostgreSQL版・SQLite版のPC）

- 元の地図から中心・ズーム・背景地図・重ね合わせタイル・図形名の表示設定と、対象の保持済みデータを複製する。本文・メモは検索のために再解析しない。DBの再検索・対象の追加取得は行わず、全選択や名前検索解除でも除外対象を復活させない。

## 回答地図のCSV出力（PostgreSQL版・SQLite版のPC）

- 「地図を印刷」の隣に「CSV出力」を配置する。反映済みの回答条件・名前検索・レイヤ表示・マーカー／図形表示を満たす対象を固定する。画面外も対象とし、表示できない位置・形状は含めない。未反映の入力は使わず、地図の再読み込みは行わない。モバイル版は既存の回答一覧CSVを維持する。
- 1回答1行。履歴モードでは同じ対象でも条件に一致する回答ごとに出力する。一覧条件と地図追加条件はそれぞれ最大10件のANDで、同一回答に適用する。最新モードは最新回答を選んでから条件を適用し、過去回答で補わない。
- 認証必須のPOST /form-answers/map-csv-check（JSON）とPOST /form-answers/map-csv-download（フォームのqueryへJSON文字列）を追加する。要求はmap-filterと同じquery/as_of・対象ID・common_form_id・conditionsで、options_onlyはfalse。毎回所有権と条件を再検証する。本文・メモを解析せずsubmitted_valuesとform_snapshotを使用する。
- 地図iframeはanswer-map-csv-requestに対して表示中の対象IDだけを返す。親origin/window・地図要求ID・CSV要求ID・反映済み更新IDを照合する。初期対象外・重複ID・古い応答を拒否し、閉じた画面や再試行前の応答は破棄する。
- 出力名はgeocode-answer-map.csv。既存の回答一覧CSVと列順・値／状態列・UTF-8 BOM・CRLF・数式対策を共通化する。最大10,000回答・200種類の回答項目。超過はエラーとし切り捨てない。200回答単位でストリーム出力し、件数・列定義・全行は同一の読み取り専用REPEATABLE READトランザクションで取得する。事前確認と実出力のトランザクションは別で、実出力でも制限を確認する。
- 事前確認はapiClientを使い、ダウンロードはauthenticated-form.tsで期限切れ時に認証を更新して同じフォームを1回再送する。0件・通信失敗でも直前の地図を保持する。通常地図・地図印刷・回答一覧CSVのAPIと出力仕様、DBスキーマは維持する。SQLite版にも同機能を反映済み。

## 所有者によるフォームからの更新（PostgreSQL版）

- PC・モバイルの地図トップのName列から開く編集モーダル下部に「入力フォーム設定」「フォームで回答を登録」を配置し、「＋更新」はテキストエディタの右下に重ねて表示する。本文末尾がボタンに隠れないよう入力欄の下側に余白を確保する。保存済みフォームに入力項目がある場合だけ「フォームで回答を登録」を表示する。公開の有効・無効や公開用パスワードとは独立し、ログインした所有者が入力できる。
- PC版の編集テキストエリアは本文欄を44vh、図形メモを36vhとし、画面内の説明・操作ボタンとのバランスを取る。
- 本文・メモ欄に「自由入力」と分析対象外の説明を常設し、「フォーム回答の分析対象にはなりません」を太字にする。PC版では説明をMarkdown操作ボタン列（map-object-edit-row）の後に配置する。追記済みの回答文を直接編集しても分析用の回答データは変更されないこと、分析するデータはフォームから登録することを案内する。案内中の「フォームで回答を登録」「入力フォーム設定」は太字にし、編集画面のボタン付近に回答保存・本文追記の説明を重複表示しない。フォーム回答のボタン名・入力画面名は「フォームで回答を登録」に統一し、回答データの保存と本文・メモへの追記を説明する。回答一覧の上部では内部入力・外部公開フォームの両方が分析対象で、本文・メモへの直接入力は含まれないことを常設表示する。確認モーダルは追加しない。
- 入力モーダルはマーカー・図形で共通。PC版の最大幅は800pxとし、狭い画面ではビューポート幅に収める。通常編集に未保存の変更がある場合は既存メッセージモーダルで確認し、保存成功後だけフォームを開く。キャンセル・保存失敗時は通常編集を保持する。背景クリックではフォーム入力を閉じない。
- 認証必須GET /marker/{id}/form/input、GET /shape/{id}/form/inputは現在のフォーム定義・設定照合トークン・引継ぎ値を返す。対象と適用元共通フォームID（個別フォームは対象単位）で最新の1回答だけを選び、form_snapshotの項目IDと型が現在定義に一致する値だけを引き継ぐ。過去回答の合成、本文・メモの再解析、定義がない回答の推測はしない。削除された選択肢は引き継がない。画像は新しい回答ごとに選択し、過去の画像は保持する。数値はブラウザへ文字列として返し、0・falseを未入力にしない。
- 認証必須POST /marker/{id}/form/submissions、POST /shape/{id}/form/submissionsは公開フォームと同じmultipart形式（submission JSONとimage\_\_項目ID）を使用する。submissionにはconfig_tokenとvaluesを含める。apiClientで認証更新・再送信し、画像の縮小・サイズ上限・サーバー検証を既存処理と共通化する。要求上限は6MiB。公開URL・公開パスワードは使用せず、対象所有権を毎回確認する。
- 過去回答を変更せず、submitted_values・form_snapshot・source_form付きの新しい履歴を追加し、マーカー本文／図形メモへ既存方式のMarkdownを追記する。履歴・画像・本文／メモは同一トランザクションで保存し、設定変更は表示時のトークンと保存時の行ロックで検出して409を返す。所有者の画像容量制限・図形メモの上限も維持する。
- 保存APIは同じトランザクションで更新した対象情報を返す。ストア・編集欄・テーブル・地図の既存オブジェクト更新通知へ反映し、後続の通常編集で追記を消さない。保存成功後はフォーム入力モーダルと元の編集モーダルを両方閉じる。通常の成功経路では地図全体を再読込しない。フォームから名前・位置・レイヤ・形状・スタイルは変更しない。
- 送信中の二重操作を防ぎ、0件や通信失敗でも通常編集を使える。フォーム取得の古い応答・閉じた画面の応答は破棄する。設定競合時は入力を保持して再読み込みを案内する。読み取り・保存応答はno-store。
- 通常編集・公開フォームのAPIと入力仕様、回答一覧・分析検索・CSV・地図印刷の動作を維持する。DBマイグレーションは不要。SQLite版にも同機能を反映済み。

## レイヤ管理の共通フォーム（PostgreSQL版）

- レイヤ設定に「共通フォームを設定」を追加する。未設定からの適用は既存・新規のマーカーと図形を対象とし、適用先にあるフォーム定義とパスワードを置き換える。公開URLと公開可否は既存対象で維持し、新規対象は公開無効を初期値とする。対象件数・置換・パスワードへの影響をメッセージモーダルで確認する。
- レイヤの適用元はlayer_model.common_form_id/common_form_version、競合確認はform_binding_revisionで保持する。対象のmanaged_layer_idで管理状態を明示する。source_formだけから管理状態を推測しない。masterの場合も実際にmasterへ所属する対象だけに適用し、集約表示される他レイヤへ波及させない。
- 共通フォームのタイトル・説明・項目変更はレイヤ管理中の対象だけへ自動反映する。従来の手動コピーの定義と適用元の版は変更しない。共通フォームの保存時に管理中レイヤ数・対象数を確認し、保存する版と件数をサーバーで再検証する。空レイヤへの設定も将来の作成へ有効。使用中の共通フォームの削除は拒否する。
- 管理中の入力フォーム設定では所定の案内を表示し、定義・適用元・個別パスワードの変更をUIとAPIの双方で拒否する。URLコピー・URL再発行・公開可否の変更だけを許可し、所有者の「フォームで回答を登録」は継続利用できる。
- 未設定への解除はフォーム設定を空にし、公開を無効にしてURLを失効させる。回答履歴・本文/メモ・画像は保持し、解除前の個別フォームを復元しない。別の管理レイヤへ移動すると移動先のフォームで置き換え、未設定レイヤへ移動すると適用済み定義を個別設定として保持する。同じレイヤ内の通常編集では再適用しない。
- 共通フォームのパスワードはハッシュのみ保存し、設定済みかどうかだけを返す。作成・編集で設定/再設定/解除できる。明示的なパスワード変更は手動コピー適用先も含めて現在同じsource_form.idを持つ対象へ反映し、手動コピーの項目定義は変えない。版・件数を確認して一括反映する。初回移行で既存対象のパスワードを変更しない。
- GET /layer/{id}/form（認証必須）は現在の適用元・版・revision・マーカー/図形件数を読み取り専用REPEATABLE READで返す。既存PUT /layer/update/{id}はupdate_common_form=trueのときだけcommon_form_id（nullで解除）・common_form_version・form_binding_revision・form_target_countを検証し、名前/アイコンと同じトランザクションで保存する。従来の引数だけならフォーム設定は変更しない。
- 共通フォームの保存はexpected_managed_countを、パスワード変更時はexpected_applied_countも検証する。影響する対象があるのに確認件数がない要求・古い版/件数は409。新規作成・移動・インポート・投稿・設定変更・削除は所有者の行ロックを先に取り、順序を統一する。一括適用中の追加も整合させ、途中の失敗は全体をロールバックする。地図表示の10,000件制限で適用対象を切り捨てない。
- 回答のsubmitted_values/form_snapshot/source_formは変更しない。必須化・項目追加/削除・選択肢変更は将来の回答だけに適用し、型変更時の新ID・削除済みIDの再使用拒否も維持する。フォームを開いた後に設定が変わった場合は照合トークンにより409を返す。公開フォームの新しいHTML/スクリプトも照合トークンを送るが、トークンがない従来の投稿形式は継続して受け付ける。
- マイグレーションは20261021120000_layer_common_forms.sql。PostgreSQL版は更新版の起動前に通常のsqlx migrate runで適用する。既存レイヤは未設定、既存対象は個別管理のまま導入し、既存URL・回答・パスワードに変更を加えない。SQLite版にも同機能を反映済み。

## レイヤ単位の自由記述制限

- レイヤ設定に「内容やメモの自由記述を制限する」を配置。初期値はOFF。切り替えは `PUT /layer/{layer_id}/input-policy` に `restrict_free_text` の真偽値だけを送信し、他の未保存設定とは独立して即時保存する。
- 成功時はON「マーカー内容・図形メモ作成の自由記述を制限しました。」、OFF「マーカー内容・図形メモの自由記述を許可しました。」を表示する。保存中は重複操作を防ぎ、失敗時はチェックを元へ戻す。
- 制限中も既存オブジェクトの名前・所属レイヤと、折れ線・ポリゴン・矩形の頂点追加・削除・移動を更新可能。本文・図形メモは読み取り専用で、空欄のプレースホルダーを「入力が制限されています。」とする。既存内容がある場合も制限の説明を常設する。Markdown・ファイル挿入、マーカー位置・円の移動・スタイル変更を制限する。頂点保存は `PUT /shape/{id}/geometry` で座標のみ送信し、サーバーの最新メモ・回答・スタイルを保持する。形状の競合は409で拒否し、表示を元に戻して再読み込みを案内する。PostgreSQL版・SQLite版とも対応済み。
- 地図上の編集とAPIにも同じ検証を適用。移動元・移動先のいずれかが制限中なら保護対象の同時変更を拒否する。マーカーは名前があれば本文が空でも更新可能。
- 本文・メモが空の新規作成、内部・外部フォームからの回答、削除は従来どおり。既存本文・回答履歴を保持し、masterの制限を他の所属レイヤに波及させない。
- version 3の `layers[].restrict_free_text` で設定を移行する。項目のない旧データはfalse。JSONの復元では既存本文・メモも取り込む。

## 既存フォーム回答の編集（PostgreSQL版・SQLite版）

- 回答一覧と詳細から共通の編集フォームを開く。所有者のみが投稿時の項目定義で編集し、回答ID・投稿日時・適用元・定義を変更しない。版番号と編集日時を追加する。履歴でも修正前の値を別回答として追加せず、最新回答の順序も維持する。
- 構造化値と生成Markdown、本文・図形メモを同一トランザクションで更新する。本文は自由記述と回答IDに対応する部分を管理し、通常編集からの回答部分の変更を拒否する。制限ONでも回答編集は可能。旧本文の対応が曖昧なら残す自由記述を確認してから再同期する。投稿時の定義がない回答は閲覧のみ。
- 画像は保持・差し替え・回答から削除を明示し、旧画像ファイルは自動削除しない。編集競合は409、保存失敗は全体を取り消す。旧JSON読み込み、20MiBのversion 3出力、画像参照のみを維持し、本文構成はファイル内回答キーで移行する。
- 保存後は一覧の基準日時とカーソルを更新し、表示中の地図・オブジェクト本文も反映する。共通UIにPinia依存を追加せず、親画面へ保存結果を通知する。
- PostgreSQL版・SQLite版とも回答編集API・DB・JSON任意項目に対応済み。回答一覧APIの `editing_supported` がtrueの場合に編集操作を表示する。投稿時定義のない旧回答は閲覧のみ。

## フォーム機能の利用案内（2026-10-22確認）

PostgreSQL版v1.34.0・v1.35.0に相当する共通フォーム、レイヤ管理、所有者入力、回答検索・編集、自由記述制限、表示切り替え、頂点編集、JSON version 3はSQLite版にも反映済み。両版とも利用者の動作確認完了という確定事項に基づく。

利用操作は[共通フォーム](../../docs/COMMON_FORMS.md)と[フォーム回答](../../docs/FORM_ANSWERS.md)を参照する。JSON入出力と回答地図のCSV・印刷/PDFはPC版、回答一覧CSVと回答編集はPC・モバイルで提供する。対象削除では編集済み・過去分を含む全回答を削除し、共通フォーム定義・画像ファイルは連動削除しない。
