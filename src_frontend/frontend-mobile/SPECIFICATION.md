# モバイル UI 仕様

## 1. 概要

モバイル専用のVueアプリ。PC版とは別のビルド・コンポーネント・ストアを持つ。バックエンドがUser-Agentに `Mobile` を含む場合にモバイルHTMLを選択する。画面幅だけでPCアプリから切り替わる構成ではない。

関連: [全体構成](../SPECIFICATION.md)、[PC版と機能差](../frontend/SPECIFICATION.md)、[地図スクリプト](../template-scripts/SPECIFICATION.md)、[Tera](../../src/templates/SPECIFICATION.md)。

## 2. ディレクトリ構成

```text
frontend-mobile/
├── index.html / public/       HTML入口・アイコン・manifest等
├── src/
│   ├── mainMobile.ts          Pinia・Router登録、初期設定取得
│   ├── AppMobile.vue          アプリ枠、ヘッダー、メモ表示
│   ├── router/               Vueルート・API URL
│   ├── views/                地図・トップ・ログイン・登録
│   ├── components/           map、map-object、layer、image、share等
│   ├── stores/               appInits、auth、layers、mapobjects等
│   ├── composables/          最終レイヤ、画像処理、図形中心等
│   ├── assets/               スタイル等
│   ├── axiosClient.ts        API通信・認証更新
│   ├── settingMobile.ts      API・資材の環境変数
│   ├── interface.ts          UIのデータ型
│   └── test/                 テスト共通設定
└── dist/                     個別ビルド成果物（生成物）
```

テストは `src/**/__tests__/` に配置する。

## 3. 起動と画面遷移

[mainMobile.ts](src/mainMobile.ts) は `/app-init` の取得終了後にマウントする。現実装ではfinally内でもinitを再度呼ぶ。[AppMobile.vue](src/AppMobile.vue) が `/mapview` に遷移し、ヘッダー・メモアイコンの表示状態をprovideする。地図画面はこれらをinjectして利用する。

| Vue内パス | 画面 | 挙動 |
| --- | --- | --- |
| `/` | `AppTopMobile.vue` | トップ用ルート |
| `/mapview` | `MapViewMobile.vue` | `/account/auth` 成功後に一覧取得を開始 |
| `/account/login` | `auth/LoginViewMobile.vue` | 通常ログイン・TOTP認証 |
| `/account/signup` | `auth/SignupViewMobile.vue` | アカウント登録 |

地図ルートの認証失敗はloginへ遷移する。ルート内のマーカー・レイヤ・画像初期取得は開始後に待機せず画面遷移する。図形取得は地図画面側でも実施する。バックエンドへの直接アクセスとVue内遷移の違いは [全体仕様](../SPECIFICATION.md) を参照。

Service Workerを登録するが、fetchの特別なキャッシュ処理はない。manifestの配置のみからオフライン利用を想定しない。

## 4. 画面・機能

[MapViewMobile.vue](src/views/MapViewMobile.vue) が、ツールバー、統合一覧、地図、各モーダル、位置共有を接続する。

| 配置 | 役割 |
| --- | --- |
| `components/map/` | ツールバー、100vhの地図iframe、全画面地図、画像表示関連 |
| `components/map-object/` | マーカー・図形の一覧、編集、公開フォーム設定 |
| `components/layer/` | レイヤの作成・選択・改名、アイコン、タイル選択 |
| `components/image/` | アップロード、一覧、プレビュー |
| `components/share/`・`qrcode/` | 一時共有URL設定・表示、QRコード |
| `components/location/` | 現在位置の共有開始・停止など |
| `components/UserPrivacySetting.vue` | アカウント設定 |
| `components/common/` | モーダル枠、通知、確認、進捗 |

PC版の印刷モーダル、JSONインポート専用モーダル、外部サイト設定コンポーネントはこのプロジェクトにはない。PC固有機能を追加・変更する際は、モバイルにも実装があると仮定しない。

地図描画・編集は `/map` が返す `map-mobile.html` と `template-map-mobile.js` が担当する。編集profileによりタップ向け文言・判定・更新差を切り替える。Vue側のMapIframeとTera側のモバイル地図UIは別の責務である。

## 5. 状態・API

| ストア | 内容 |
| --- | --- |
| `appInits` | タイトル、登録・パスワード変更許可、許可origin |
| `auth` | UI認証状態、再認証・トークン切り替え中フラグ |
| `layers` | レイヤ一覧と更新操作 |
| `mapobjects` | マーカーと統合検索の図形ID |
| `shapes` | 図形データ、GeoJSON等の更新 |
| `images` | 初期50件・検索結果のファイル一覧 |
| `markerIcons` | マーカーアイコン一覧・検索等 |

主なAPI URLは [router/urls.ts](src/router/urls.ts)、データ型は [interface.ts](src/interface.ts)。ストアはPCと別ファイルなので、フィールドや更新方法の変更は両方確認する。

[axiosClient.ts](src/axiosClient.ts) はCookie付き通信を行い、FormDataのContent-Typeはブラウザに任せる。401 `token_expired` は共有Promiseで `/account/refresh` を実行し再試行する。更新失敗・refresh期限切れはログインへ戻す。再認証・トークン切り替え中は先行遷移を抑止する。

`useLastActiveLayer` はlocalStorageの `geocode-web:last-active-layer-id` を使い、利用可能なレイヤに存在しなければmasterへ戻す。キーはPCと同名でアカウントIDを含まない。ログイン画面には `loginuser` / `loginUser` キーも存在する。地図側の保存値は [地図仕様](../template-scripts/SPECIFICATION.md) を参照する。

## 6. iframe連携

[MapIframe.vue](src/components/map/MapIframe.vue) は `focus`、`mapObjectFilter`、`mapObjectUpdate`、`mapObjectDelete`、`tileOverlaysUpdate` を送信する。更新系要求はrequestIdで対応付け、2秒で未応答をfalseにする。画面破棄時は待機中要求を解除する。

受信する通知は再読み込み、ログイン遷移、画像表示、現在位置、更新結果。画像通知はPCの `callParentFunction` と異なり **`callParentImagePreview`** を使う。印刷開始通知のハンドラーは持たない。

送信先はiframe URLのorigin、受信はapp-init由来の許可originとiframeのcontentWindowの両方で検証する。位置情報を利用するiframeには `allow="geolocation"` を設定する。完全なデータ形式は [メッセージ仕様](../template-scripts/SPECIFICATION.md) を参照する。

## 7. 開発・ビルド・検証

このディレクトリで実行する:

```sh
npm ci
npm run dev
npm run type-check
npm run test:run
npm run build
```

`settingMobile.ts` は `VITE_IP_ADDRESS` と `VITE_ASSET_PATH` を参照する。Viteはルートの環境変数を読み、個別成果物は `dist/index.html`。統合時に `index-mobile.html` に改名する。地図のvendor資材はPC側のビルドが供給するため、配布には [統合手順](../SPECIFICATION.md) を使用する。

既存テストはrouter、Axios、ストア、画像処理、モーダル、iframe、位置共有などを対象とする。モバイル地図の描画・entryの連携テストはtemplate-scriptsおよびPC側 `tests/template-js/` にも存在する。

タッチ・ペン入力、画面回転、位置情報の許可、アップロードと動画再生などは実端末での確認が別途必要。jsdomのテスト成功を実端末確認済みと解釈しない。


## 共通フォーム管理・適用

- 上部ツールバーの「共通フォーム」から `CommonFormsModal.vue` を開く。PCは `left-btn-header-zone`、モバイルは上部ツールバーに配置する。
- 「作成」「一覧」で操作を切り替え、新規作成、一覧取得、編集、保存、削除を行う。保存・削除後は一覧を更新する。読み込み失敗時は再読み込みできる。
- 項目編集は `MapObjectFormSettingsModal.vue` の共通フォームモードを再利用する。対象別フォームと同じ入力型・検証を使用し、共通フォームモードには公開URL・パスワード・公開状態の操作を表示しない。
- 対象別の「入力フォーム」ではプルダウンから共通フォームを選び、置換を確認して読み込む。保存するまで対象へ確定しない。公開状態・URL・パスワードは維持する。
- 適用元ID・版と項目IDを維持して保存する。項目の種類変更時には新しいIDを発行する。意味を変更する場合は削除・追加を案内する。
- 共通フォームの変更は既存のコピーに波及しない。削除確認で適用済みフォーム・回答履歴が残ることを説明する。
- 更新競合（409）は開き直して再編集するよう案内する。保存・適用中は編集操作を無効にし、失敗時は入力内容を保持してメッセージを表示する。
- 小さい画面では入力欄を縦配置し、モーダル内をスクロールして操作する。

- 共通フォームの入口には `form_24.png` を使用する。作成・一覧の切替はレイヤ作成と同じ `layer-type` のラジオ形式。見出し・切替・再読み込み欄はスクロール領域の外に置き、フォーム一覧だけをスクロールする。
- 共通フォームの削除・コピー適用は既存の `MessageModal` に実行ボタンを表示して確認する。閉じる・オーバーレイ操作では実行しない。
- 適用欄ではプルダウンと「共通フォームを使用する」ボタンを横並びにする。

- 共通フォーム管理の作成・一覧ラジオ間隔は32pxとし、閉じるボタンは既存モーダルと同じグレー背景のスタイルに統一する。


## 回答履歴・最新回答・CSV（第2段階）

- `components/map-object/FormAnswersModal.vue` が回答一覧・条件検索・詳細表示・CSV出力を担当する。
- 共通フォーム管理の全件入口、各共通フォームの回答一覧、対象別入力フォームの回答履歴から開く。削除済み共通フォームも回答の検索候補へ含める。
- 履歴／最新回答を切り替え、共通フォーム・版・対象種別・対象ID・名前・レイヤ・投稿日時・型別の回答条件で検索する。回答条件は最大10件のAND。最新選択後に版・期間・回答条件を適用する。
- PCは表、700px以下はカード形式。表示項目を選択でき、詳細には投稿時の項目名・順序・値を表示する。定義なしの旧回答は項目IDで表示する。
- 検索とページ移動はサーバーで実施し、次ページは検索基準日時とカーソルを維持する。表示は50件単位。
- CSVは表示中の検索結果を全件出力する。未検索の条件編集を混ぜない。事前検証後に通常のフォーム送信でダウンロードし、JavaScriptのBlobへ全件を蓄積しない。上限は10,000回答・200項目。
- 入力日時は端末のタイムゾーンからUTCへ変換し、表示日時は端末のタイムゾーンを使用する。CSVの日時はUTCと明記する。
- 詳しい検索・旧回答・CSV列・所有権の仕様はルート `SPECIFICATION.md` の第2段階を参照する。

- 共通フォーム管理の見出しには `modal-h2` を使用する。全フォームの「回答一覧と分析」は作成タブの作成ボタンの隣にボタンとして配置し、一覧タブは各フォームの回答一覧ボタンのみを表示する。
- 共通フォーム管理・項目編集のボタン（上下移動・項目削除を除く）は `btn-close` を付け、`form-modal-buttons.css` で既存のグレー背景ボタンと同じスタイルに統一する。確認メッセージも同じ配色とする。回答一覧のボタンもグレー背景に統一する。

### 回答一覧の操作と表示

- CSV隣の「地図で確認」は反映済みの検索条件・基準日時で全ページの対象を開く。`AnswerMapModal.vue` が `/form-answers/map` へ通常のPOSTフォームを送り、返却された閲覧専用地図をiframeに表示する。対象重複はサーバーで除去する。
- 地図は100dvhの半透明オーバーレイに、余白・角丸を持つ高さ95dvhのコンテンツを重ね、セーフエリアを確保する。回答数／対象数は上部、閉じるボタンは画面左下へ固定し、地図の読み込み中も閉じられる。メッセージのorigin・source・request_idを検証し、失敗・タイムアウト時は再試行を案内する。閉じた後も一覧の状態は保持する。上限等はルート仕様の第3段階を参照。

- 検索項目・表示項目候補（column-options）・テーブル列はフォームの入力順とする。共通フォームの新しい版または対象の現在設定を優先し、過去だけの項目は末尾に追加する。表示列のチェックを外して再選択しても入力順を維持する。

- 初期状態は検索欄を閉じ、回答を自動表示。「絞り込み」で基本条件、「詳しい条件」で版・対象種別・レイヤを開く。条件は「絞り込む」または「変更を反映」で適用し、検索欄の開閉状態を維持する。「条件を追加」「条件をクリア」「絞り込む」は横一列に配置する。未反映の変更を表示し、ページ移動・CSVには反映済みの条件を使用する。
- 対象IDは直接入力せず、内部の対象範囲を維持する。条件クリアでも呼び出し元のフォーム・対象範囲は維持する。表示モードは変更しない。
- 項目名を基本表示とし、同名項目は種類と番号で区別する。UUID等は詳細の折りたたみ「管理用情報」へ移動する。定義のない旧回答は「項目名不明の項目 N」と表示する。
- 700px以下はカードで回答項目を先頭3件まで表示し、ラベルと値を横並びにする。値に約7割の幅を割り当て、長文は2行まで表示する。全項目は「詳細を見る」で確認する。表示モード・絞り込み・更新を横一列、基本条件は共通フォーム・対象名と開始日時・終了日時の2行、詳しい条件は3列（対象種別を狭くする）に配置する。複数選択はチェックボックス、操作ボタンはヘルプの「?」を除き高さ40px以上とする。広い画面はPCと同じ表形式。CSVの列・識別子・検索順序は変更しない。
- 広い画面の表は地図トップと同じ濃色見出し・交互背景・ホバー色を使用し、見出し固定で一覧内をスクロールする。基本条件は1000px超で4列、701〜1000pxで2列、詳しい条件は701px以上で3列とする。
- 一覧・CSVの説明はCSV横の22pxの「?」で開閉する。日時の説明文とCSVダウンロード開始の成功メッセージは表示しない。回答詳細は長い文字列を折り返して横方向にはみ出さないようにする。

- 共通フォーム管理は「作成」を初期タブとする。タイトルはモーダル幅全体で中央寄せ・下線表示し、閉じるボタンは右上に配置する。作成タブの「回答一覧と分析」は作成ボタンの隣のボタンとして表示する。背景クリックでも閉じる。
- 対象別入力フォームの回答履歴は共通フォーム適用操作と横並びに配置する。公開URLの「フォームを確認」はURLコピーと同じグレーのボタンスタイル、「URLを再発行」は青（`#1c3abe`）。項目の上下移動・削除は従来の白背景（削除は赤文字）を維持する。

- 「共通フォームの作成」「共通フォームの編集」の見出しには `modal-h2` を付けない。管理モーダルのタイトルは全幅中央・下線を維持し、狭い画面では右上の閉じるボタンとタイトルを別行に配置する。

- モバイルの共通フォーム作成・管理ボタンは `MapViewMobile.vue` の `#function-btn-row` に配置し、同列のアイコンボタンと同じスタイルを使う。上部 `MapToolbar` には表示しない。
- 対象別の入力フォームでは共通フォームの選択欄と適用ボタンを折り返さず横並びにする。「フォームへの回答」ラベルと「回答履歴を開く」ボタンは表示しない。回答の閲覧は共通フォーム管理から行う。

## 回答地図の追加絞り込み

- PostgreSQL版先行。回答地図専用の `form-answer-map.html` / `form-answer-map.ts` を使用し、通常の `map-anather` と印刷の経路を維持する。SQLite版は変更しない。
- PC・モバイルのAnswerMapModalは同一構成。共通フォームと最大10件のAND条件で初期対象を絞る。日付・数値の範囲は両端を含む。0・false・未入力・項目なしを区別する。値はsubmitted_values、定義はform_snapshotを使用する。
- 初期map APIから取得したquery/as_ofと対象IDをmap-filter JSON APIに渡す。候補は追加条件で狭めず、0件でも編集・解除できる。候補・件数・検索は読み取りトランザクション内で取得する。
- answer-filter.tsはorigin・親window・requestId・更新IDを確認し、初期対象の部分集合だけを受け付ける。対象IDは種別を含む。保持済みレイヤを再利用し、iframeを再読み込みしない。中心・ズーム・名前検索・レイヤ選択を保持する。
- 共通検索のisRecordAllowedは任意の判定関数。未指定の通常地図は従来動作。回答地図では検索解除・レイヤ切替でも追加条件を維持する。表示件数は実際に表示中のレイヤを数え、表示不可の対象と区別する。
- 失敗時は直前の地図を維持し、古い応答・閉じた画面の応答を破棄する。解除は元の一覧条件へ戻す。範囲変更は「表示対象に合わせる」で明示的に行う。閉じるボタンは左下。一覧状態・通常地図設定は保存変更しない。
- answer-preview.tsは初期の範囲調整・件数・query/targetsのready通知を担当する。失敗はform-answer-map-error.htmlで通知する。HTMLのJSON値はjson_encode_for_html経由とし、成功・失敗ともno-store。
- 色分けUI・凡例は追加絞り込みへ置き換える。answer-analysis.tsと任意analysis入力は旧呼び出しの互換性維持に限って残す。
- 回答地図のPC表示（幅701px以上）は絞り込みを左20%、地図を右80%に配置する。右下の開閉ボタンで絞り込み全体を隠し、地図を全幅へ広げる。開閉ではiframe・入力条件を保持する。幅700px以下は上部配置を維持し、操作ボタンを等幅2列、フォーム選択を全幅に配置する。狭い画面への切替時も絞り込みを操作可能にする。
- モバイル版はanswer-map-mobile-layoutを指定し、タブレット・横向きなど幅701px以上でも絞り込みを地図の上に配置する。
- 回答地図のPC版ヘッダーはapp-headerと同じ黒背景・whitesmoke文字とし、モバイル版ヘッダーは従来の白系背景を維持する。

## 回答地図・CSVの認証更新

- PostgreSQL版のPC・モバイル共通。地図初回表示・再試行とCSV実ダウンロードは、authenticated-form.tsを介してネイティブフォーム送信する。CSVをBlobへ蓄積せず、既存のストリーム出力を維持する。
- map/downloadのPOSTへnative_request_id・native_parent_originをクエリで付ける。CookieValidatorは従来どおり認証し、期限切れの401だけをnative-form-auth-error通知HTMLへ変換する。通知指定なしは従来の401 JSON。成功応答・その他のエラー・検索条件・本文形式は変更しない。
- 親はorigin・iframeのcontentWindow・要求IDを検証し、apiClient経由のGET /account/authで既存のリフレッシュ・再試行処理を実行する。成功後、同じフォーム内容を最大1回だけ再送する。認証更新失敗や再送後の401はエラーを表示する。
- 古い通知・重複通知は無視し、画面を閉じた場合や別の送信を始めた場合は待機処理を解除する。地図はready/error時にも解除し、CSVの通知待機は最大120秒。追加絞り込み・回答一覧・CSV事前確認は従来どおりapiClientを使用する。
- SQLite版は変更しない。既存の認証Cookie属性・リフレッシュAPI・DBスキーマは変更しない。

## 回答地図の印刷（PostgreSQL版・PC先行）

- 回答地図の「地図を印刷」またはCtrl+P / Command+Pから既存の印刷プレビューを開く。モバイル版は印刷UIを表示しない。用紙・タイトル・印刷・PDF出力・画像読み込み待機は共通処理を使用する。
- 印刷開始時点で、反映済みの回答条件・名前検索・レイヤ表示・マーカー/図形表示をすべて満たす対象を固定する。画面外の対象も保持し、用紙上の範囲はプレビューで調整できる。未反映の条件編集は使用しない。更新中・0表示対象では起動しない。
- 元の地図から中心・ズーム・背景地図・重ね合わせタイル・図形名の表示設定と、対象の保持済みデータを複製する。本文・メモは検索のために再解析しない。DBの再検索・対象の追加取得は行わず、全選択や名前検索解除でも除外対象を復活させない。
- 対象は最大10,000件、転送データはUTF-8 JSONで32MiBまで。超過時は切り捨てず条件を絞るよう案内する。送信元origin/window・地図要求ID・条件更新ID・印刷要求IDを照合する。印刷スナップショットは印刷中に変更しない。
- 認証必須POST /form-answers/map-printはform-answer-map-print.htmlの枠だけを返す。parent_origin・request_idを検証し、Cache-Controlはno-store。対象データは親からpostMessageで受け取る。初回表示・再試行の401はauthenticated-form.tsによる認証更新と1回の再送に対応する。
- 専用entry form-answer-map-print.tsで検証したスナップショットを初期化し、print-preview.tsの共通処理へ渡す。通常の/map-another?print=1の初期化は従来どおり。印刷キーは最前面の回答地図・印刷プレビューへ接続する。
- 閉じた後は元の回答地図の条件・中心・ズーム・レイヤ状態を維持する。通常地図の保存設定、DBスキーマ、SQLite版は変更しない。

## 回答地図のCSV出力（PostgreSQL版・PC先行）

- 「地図を印刷」の隣に「CSV出力」を配置する。反映済みの回答条件・名前検索・レイヤ表示・マーカー／図形表示を満たす対象を固定する。画面外も対象とし、表示できない位置・形状は含めない。未反映の入力は使わず、地図の再読み込みは行わない。モバイル版は既存の回答一覧CSVを維持する。
- 1回答1行。履歴モードでは同じ対象でも条件に一致する回答ごとに出力する。一覧条件と地図追加条件はそれぞれ最大10件のANDで、同一回答に適用する。最新モードは最新回答を選んでから条件を適用し、過去回答で補わない。
- 認証必須のPOST /form-answers/map-csv-check（JSON）とPOST /form-answers/map-csv-download（フォームのqueryへJSON文字列）を追加する。要求はmap-filterと同じquery/as_of・対象ID・common_form_id・conditionsで、options_onlyはfalse。毎回所有権と条件を再検証する。本文・メモを解析せずsubmitted_valuesとform_snapshotを使用する。
- 地図iframeはanswer-map-csv-requestに対して表示中の対象IDだけを返す。親origin/window・地図要求ID・CSV要求ID・反映済み更新IDを照合する。初期対象外・重複ID・古い応答を拒否し、閉じた画面や再試行前の応答は破棄する。
- 出力名はgeocode-answer-map.csv。既存の回答一覧CSVと列順・値／状態列・UTF-8 BOM・CRLF・数式対策を共通化する。最大10,000回答・200種類の回答項目。超過はエラーとし切り捨てない。200回答単位でストリーム出力し、件数・列定義・全行は同一の読み取り専用REPEATABLE READトランザクションで取得する。事前確認と実出力のトランザクションは別で、実出力でも制限を確認する。
- 事前確認はapiClientを使い、ダウンロードはauthenticated-form.tsで期限切れ時に認証を更新して同じフォームを1回再送する。0件・通信失敗でも直前の地図を保持する。通常地図・地図印刷・回答一覧CSVのAPIと出力仕様、DBスキーマ、SQLite版は変更しない。

## 所有者によるフォームからの更新（PostgreSQL版）

- PC・モバイルの地図トップのName列から開く編集モーダル下部に「入力フォーム設定」「フォームで回答を登録」を配置し、「＋更新」はテキストエディタの右下に重ねて表示する。本文末尾がボタンに隠れないよう入力欄の下側に余白を確保する。保存済みフォームに入力項目がある場合だけ「フォームで回答を登録」を表示する。公開の有効・無効や公開用パスワードとは独立し、ログインした所有者が入力できる。
- 本文・メモ欄に「自由入力」と分析対象外の説明を常設し、「フォーム回答の分析対象にはなりません」を太字にする。PC版では説明をMarkdown操作ボタン列（map-object-edit-row）の後に配置する。追記済みの回答文を直接編集しても分析用の回答データは変更されないこと、分析するデータはフォームから登録することを案内する。案内中の「フォームで回答を登録」「入力フォーム設定」は太字にし、編集画面のボタン付近に回答保存・本文追記の説明を重複表示しない。フォーム回答のボタン名・入力画面名は「フォームで回答を登録」に統一し、回答データの保存と本文・メモへの追記を説明する。回答一覧の上部では内部入力・外部公開フォームの両方が分析対象で、本文・メモへの直接入力は含まれないことを常設表示する。確認モーダルは追加しない。
- 入力モーダルはマーカー・図形で共通。通常編集に未保存の変更がある場合は既存メッセージモーダルで確認し、保存成功後だけフォームを開く。キャンセル・保存失敗時は通常編集を保持する。背景クリックではフォーム入力を閉じない。
- 認証必須GET /marker/{id}/form/input、GET /shape/{id}/form/inputは現在のフォーム定義・設定照合トークン・引継ぎ値を返す。対象と適用元共通フォームID（個別フォームは対象単位）で最新の1回答だけを選び、form_snapshotの項目IDと型が現在定義に一致する値だけを引き継ぐ。過去回答の合成、本文・メモの再解析、定義がない回答の推測はしない。削除された選択肢は引き継がない。画像は新しい回答ごとに選択し、過去の画像は保持する。数値はブラウザへ文字列として返し、0・falseを未入力にしない。
- 認証必須POST /marker/{id}/form/submissions、POST /shape/{id}/form/submissionsは公開フォームと同じmultipart形式（submission JSONとimage__項目ID）を使用する。submissionにはconfig_tokenとvaluesを含める。apiClientで認証更新・再送信し、画像の縮小・サイズ上限・サーバー検証を既存処理と共通化する。要求上限は6MiB。公開URL・公開パスワードは使用せず、対象所有権を毎回確認する。
- 過去回答を変更せず、submitted_values・form_snapshot・source_form付きの新しい履歴を追加し、マーカー本文／図形メモへ既存方式のMarkdownを追記する。履歴・画像・本文／メモは同一トランザクションで保存し、設定変更は表示時のトークンと保存時の行ロックで検出して409を返す。所有者の画像容量制限・図形メモの上限も維持する。
- 保存APIは同じトランザクションで更新した対象情報を返す。ストア・編集欄・テーブル・地図の既存オブジェクト更新通知へ反映し、後続の通常編集で追記を消さない。保存成功後はフォーム入力モーダルと元の編集モーダルを両方閉じる。通常の成功経路では地図全体を再読込しない。フォームから名前・位置・レイヤ・形状・スタイルは変更しない。
- 送信中の二重操作を防ぎ、0件や通信失敗でも通常編集を使える。フォーム取得の古い応答・閉じた画面の応答は破棄する。設定競合時は入力を保持して再読み込みを案内する。読み取り・保存応答はno-store。
- 通常編集・公開フォームのAPIと入力仕様、回答一覧・分析検索・CSV・地図印刷の動作を維持する。DBマイグレーションは不要。SQLite版は変更しない。

## レイヤ管理の共通フォーム（PostgreSQL版）

- レイヤ設定に「共通フォームを設定」を追加する。未設定からの適用は既存・新規のマーカーと図形を対象とし、適用先にあるフォーム定義とパスワードを置き換える。公開URLと公開可否は既存対象で維持し、新規対象は公開無効を初期値とする。対象件数・置換・パスワードへの影響をメッセージモーダルで確認する。
- レイヤの適用元はlayer_model.common_form_id/common_form_version、競合確認はform_binding_revisionで保持する。対象のmanaged_layer_idで管理状態を明示する。source_formだけから管理状態を推測しない。masterの場合も実際にmasterへ所属する対象だけに適用し、集約表示される他レイヤへ波及させない。
- 共通フォームのタイトル・説明・項目変更はレイヤ管理中の対象だけへ自動反映する。従来の手動コピーの定義と適用元の版は変更しない。共通フォームの保存時に管理中レイヤ数・対象数を確認し、保存する版と件数をサーバーで再検証する。空レイヤへの設定も将来の作成へ有効。使用中の共通フォームの削除は拒否する。
- 管理中の入力フォーム設定では所定の案内を表示し、定義・適用元・個別パスワードの変更をUIとAPIの双方で拒否する。URLコピー・URL再発行・公開可否の変更だけを許可し、所有者の「フォームで回答を登録」は継続利用できる。
- 未設定への解除はフォーム設定を空にし、公開を無効にしてURLを失効させる。回答履歴・本文/メモ・画像は保持し、解除前の個別フォームを復元しない。別の管理レイヤへ移動すると移動先のフォームで置き換え、未設定レイヤへ移動すると適用済み定義を個別設定として保持する。同じレイヤ内の通常編集では再適用しない。
- 共通フォームのパスワードはハッシュのみ保存し、設定済みかどうかだけを返す。作成・編集で設定/再設定/解除できる。明示的なパスワード変更は手動コピー適用先も含めて現在同じsource_form.idを持つ対象へ反映し、手動コピーの項目定義は変えない。版・件数を確認して一括反映する。初回移行で既存対象のパスワードを変更しない。
- GET /layer/{id}/form（認証必須）は現在の適用元・版・revision・マーカー/図形件数を読み取り専用REPEATABLE READで返す。既存PUT /layer/update/{id}はupdate_common_form=trueのときだけcommon_form_id（nullで解除）・common_form_version・form_binding_revision・form_target_countを検証し、名前/アイコンと同じトランザクションで保存する。従来の引数だけならフォーム設定は変更しない。
- 共通フォームの保存はexpected_managed_countを、パスワード変更時はexpected_applied_countも検証する。影響する対象があるのに確認件数がない要求・古い版/件数は409。新規作成・移動・インポート・投稿・設定変更・削除は所有者の行ロックを先に取り、順序を統一する。一括適用中の追加も整合させ、途中の失敗は全体をロールバックする。地図表示の10,000件制限で適用対象を切り捨てない。
- 回答のsubmitted_values/form_snapshot/source_formは変更しない。必須化・項目追加/削除・選択肢変更は将来の回答だけに適用し、型変更時の新ID・削除済みIDの再使用拒否も維持する。フォームを開いた後に設定が変わった場合は照合トークンにより409を返す。公開フォームの新しいHTML/スクリプトも照合トークンを送るが、トークンがない従来の投稿形式は継続して受け付ける。
- マイグレーションは20261021120000_layer_common_forms.sql。PostgreSQL版は更新版の起動前に通常のsqlx migrate runで適用する。既存レイヤは未設定、既存対象は個別管理のまま導入し、既存URL・回答・パスワードに変更を加えない。SQLite版は変更しない。
