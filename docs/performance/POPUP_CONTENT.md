# ポップアップ本文の段階表示と負荷計測

2026年10月26日、画像専用の追加表示を、本文全体の「さらに読み込む」に置き換えた。比較前はコミット `aa8370b`。画像のない長文でも、本文全体の解析とポップアップ開封時のレイアウトに時間がかかっていたため、HTML・DOMの生成とインライン解析を必要な範囲に限定した。

## 計測条件と指標

- 同じWindows端末のHeadless Chrome `155.0.8059.85`、画面1000×800、各ケース3回の中央値。実際のLeaflet・Marked・XSS処理を使用。
- 「準備」は本文の表示準備。「開封同期」は準備済みポップアップの `openPopup()` が戻るまで。別々に計測しており、合計を直接測ったクリック応答時間ではない。
- DOM数はポップアップの子孫要素数で、タイトル・操作UI・Leafletの要素を含む。計測時の段階表示の200要素予算は本文のみを数える。
- 画像は同一端末で配信する32×32のSVG。実画像の通信・デコード時間は比較対象に含めない。
- フェーズ別タイマーには包含関係があり、各値を加算して総時間にしない。

## 変更前後

時間はms。「前 → 後」は同一ケースの中央値。

| 本文 | 準備 | 開封同期 | 初期DOM数 |
|---|---:|---:|---:|
| 装飾・リンク付き文章300段落 | 7.2 → 0.7 | 30.8 → 10.1 | 918 → 152 |
| 装飾・リンク付き文章3000段落 | 235.4 → 4.5 | 271.4 → 9.3 | 9018 → 152 |
| 日付と画像600枚 | 6.8 → 1.2 | 32.2 → 9.0 | 1518 → 223 |
| リスト3000項目 | 38.7 → 9.0 | 283.2 → 9.8 | 9019 → 171 |
| 表1000行×5列 | 12.0 → 1.1 | 146.9 → 6.9 | 8027 → 191 |
| 装飾を大量に含む単一段落 | 448.3 → 1.0 | 141.6 → 9.0 | 6019 → 110 |
| HTML本文3000段落 | 6.3 → 0.9 | 198.4 → 9.4 | 9019 → 223 |
| 閉じたdetails 300個 | 3.7 → 1.6 | 31.3 → 14.2 | 618 → 223 |
| 長文を含む閉じたdetails 1個 | 0.8 → 0.9 | 2.3 → 2.8 | 20 → 22 |

長文details 1個の展開同期時間は365.2 → 10.3ms、展開直後のDOM数は9020 → 156となった。閉じた状態ですでに軽量だった同ケースの開封時間はわずかに増加している。

3000段落の比較前は、準備のうちLexerが213.5ms、開封中のレイアウトが227.1msだった。追加調査では、不要な拡張構文の開始位置走査を省き、ブロック構造と参照定義だけを先に解析する方法が有効だった。インライン解析は表示する範囲に遅延し、長い単一段落・リスト・表・コード・HTMLも途中で区切る。

## 1回の表示量と累積表示後の更新

初回と追加操作には同じ予算を使う。実データでの確認を受け、現在は計測時の約2倍に調整している。

- 本文の新規要素は最大400要素、追加テキストは最大24000文字を目安とする。画像枚数固定ではなく、見出し・文章・表・リスト等も含める。タイトルと操作UIは別枠。
- さらに2048操作、または約24msで生成ループを区切る。要素数・文字量より先に処理量の上限で止まる場合もあるため、これらの上限も2倍にした。時刻は32操作ごとに確認し、出力のない区切りでは次のフレームへ継続する。24msは処理を区切る目安であり、解析・安全化・レイアウトを含む操作全体の時間上限ではない。
- 初期実装では100・200・400要素の候補を単純な文章の抜粋で比較し、200要素候補の開封中央値2.4msを確認した。掲載した計測結果とJSONは、その後採用した200要素・12000文字・1024操作・約12msの設定によるもので、現在の設定で再計測した値ではない。

段階表示後も本文DOMは累積する。ポップアップの外寸と内容の幅が変わらないときは、Leafletによる本文の取り外し・再挿入と再計測を省く。寸法変化・画像や動画の読込時には必要な更新を行い、内部スクロール位置を保つ。

3000段落で最初の追加操作後にさらに10回追加した場合、最後の追加操作は寸法キャッシュ導入前34.8ms、導入後4.2msだった。同じ状態でアプリのレイアウト更新を5回要求しても、導入後のLeaflet本体の更新呼び出しは0回だった。Leafletの `update()` を直接5回呼ぶと98.7msかかるため、本文を小分けにする処理に加え、不要な再計測の抑制も必要だった。

## 結果の範囲

この端末では、多量本文の同期処理と初期DOM数の削減を確認した。iOS・iPadOSの実機測定ではなく、全端末・全本文の改善を保証する結果ではない。追加表示を続けた後はDOMが増えるため、全文表示時のメモリ・ブラウザ描画負荷は残る。

2回の `requestAnimationFrame` を待った `openToFrameMs` は直接の描画完了測定ではない。日付と画像600枚では54.1 → 79.1msと増加し、HTML本文では変更後も161.7msとばらつきがあった。同期処理の短縮だけで、画像取得完了や画面表示までの全ケースが短縮したとは判断しない。最終的な体感とスクロールは対象のiOS・iPadOS実機でも確認する。

表示仕様、検索と印刷の扱いは[地図表示](../MAP_VIEWING.md#popup-content)と[地図印刷](../MAP_PRINTING.md)を参照。
