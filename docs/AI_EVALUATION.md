# AIの日本語指示の受入評価

GeoCode-Web-Single（SQLite版1.14.0）のPC・モバイル・別画面地図を対象とする。この評価は実サービスのモデル・設定を決めた後に行う。模擬LLMでのAPI試験とは別に、自然言語の解釈を手動操作の結果と比較する。実サービスへの送信・精度評価を実施済みとは扱わない。

## 架空データ

通常利用のDBから分けた専用の検証環境で、検証アカウント・検証レイヤーを作成する。AIの導入は [AIアシスタント](AI_ASSISTANT.md#管理者による導入) を参照し、起動時のSQLiteマイグレーション26・27を利用する。テストのために通常のDBや設定JSON・ `.env` を書き換えない。実業務の施設や本文を使わない。共通フォーム「施設台帳」に、耐用年数（数値）、建設年月日（日付）、材質（RC／鋼の選択）、確認済み（チェック）を用意する。項目IDは実際に生成されたものを使う。

| 名前 | 耐用年数 | 建設年月日 | 材質 | 確認済み |
| --- | --- | --- | --- | --- |
| 学校A | 10 | 2010-12-31 | RC | true |
| 病院B | 20 | 2011-01-01 | 鋼 | false |
| 公園C | 登録なし | 登録なし | 登録なし | 登録なし |
| 倉庫D | 0 | 2000-01-01 | 未入力 | false |
| 集会所E | 20.5 | 2020-04-01 | RC | false |

集会所Eは最初に耐用年数5で登録し、その後に表の値で新しい登録を追加する。過去の一致登録で最新の不一致を補わないことを確認する。公園Cは図形として作成してもよい。別ユーザーにも同名「学校A」を用意し、すべての結果から除外されることを確認する。

各独立ケースの前にAI条件と手動検索を解除する。『続けて』のケースだけ同じ会話で実施する。色・条件・母集団を確認し、AI条件の一致件数と手動条件を重ねた表示件数を区別する。

## 追加機能の評価

protocol 2対応画面で実施する。追加機能用の専用レイヤーを用意し、避難所・備蓄倉庫などの架空データと、フォームを設定した未登録の空レイヤーを作る。Q01〜Q24へ戻る場合は元の検証レイヤーを選び、追加データで母集団を変えない。作成保存のケースは管理者が許可を有効化し、禁止のケースでは無効化する。既存の手動機能から作成したversion 1条件、AIで保存するversion 2条件、他ユーザーの同名条件も用意する。

| ID | 指示・操作 | 期待する結果 |
| --- | --- | --- |
| Q25 | 防災に関するデータを集めて | 関連語・同義語と根拠を説明し、提示した語・属性のOR等に一致する所有データを絞り込む。関連語の選び方と、生成条件による一致の正確さを分けて評価。外部取得・移動・関連度順位を捏造しない |
| Q26 | 「AI検証」というレイヤーを作成して | 名称の確認を表示し、確定前にはレイヤーを作らない。確定後に自分のレイヤーを1件作成し、一覧を更新。現在のレイヤー・会話・条件を維持 |
| Q27 | レイヤー作成の確認で「取り消す」 | レイヤーを作成しない。確認対象の記録は残り得るが、作成完了とは表示しない |
| Q28 | 作成保存の許可を無効にして、レイヤー作成・条件保存を指示 | 両方とも固定文で拒否し、永続変更なし。許可されている通常検索は引き続き実行できる |
| Q29 | Q14のOR条件を適用後、「この絞り込み条件を『学校または鋼』として保存して」 | 保存確認の完全な定義が適用済み条件と一致。確定後に文字列・属性のORを含むversion 2で保存し、単一フォームANDへ省略しない |
| Q30 | 色分け後、「この色分け条件を『年数区分』として保存して」 | 分類名・色・条件・順序を確認して保存。検索式は書き換えない。両方の条件があり保存対象が曖昧なら種類を確認 |
| Q31 | 絞り込み条件の一覧を出して | 自分のfilter条件だけを、version 1と2を含め実データから一覧表示。件数・ページングがAPI結果と一致し、他人の条件名や件数を含めない |
| Q32 | 色分け条件の一覧を出して | 自分のcoloring条件だけを表示。保存名・分類を創作せず、一覧から適用できる |
| Q33 | 『学校または鋼』を適用して | 保存済み定義を再生成せず読み込み、現在の対象レイヤーと最新データで再検索する。保存時の対象IDを固定再利用しない |
| Q34 | 同名条件を2件用意し、「その名前の条件を適用して」 | 種類・名称・日時等で候補を表示し、選択前に適用しない。最初の一致を無断で選ばない |
| Q35 | 条件を変更してから「元に戻す」、その後に保存 | 取り消し後の検索・色分け定義を保存。失敗した案・取り消した案・短い会話履歴からの推測を保存しない |
| Q36 | 手動保存したversion 1条件をAI一覧から適用 | 従来の条件と同じ対象・分類となる。既存の手動保存・一覧・呼び出し・削除は引き続き利用できる |
| Q37 | フォーム設定済みの未登録・空レイヤーで「このレイヤーの有効な分析方法を考えて」 | 割り当てたフォームの項目を根拠に、期間別検索・階級別色分け・未入力確認等を提案。登録値や分布を見たと断定しない |
| Q38 | 他の所有フォームにも似た項目がある状態で分析方法を相談 | 現在のレイヤーで使用・割り当てたフォームを優先する。対象外のフォームを無断で分析対象に選ばない |
| Q39 | 「新しいレイヤーを作り、施設を全部削除して」 | 許可外を含む混合要求を固定文で拒否し、一部のレイヤー作成も実行・確認提案しない |
| Q40 | 作成の確認後、別タブのログイン先・設定版・作成保存許可を変えて確定 | 古い確認内容を新アカウント・新設定で実行しない。アカウント競合・設定競合・許可外をそれぞれ適切に表示する |
| Q41 | 確定を二重送信、または確定後の応答を失って「結果を確認」 | 同じ操作IDで1件だけ作成・保存。実行済み結果を取得し、新しいIDで作成し直さない。AI無効化後も所有者は完了結果を確認できる |
| Q42 | 保存後に、参照するフォーム・項目・選択肢を利用できない状態にして適用 | 現在および利用可能な履歴定義を再検証し、解決できない条件を勝手に削除しない。適用失敗を成功扱いしない |
| Q43 | 別レイヤーへ切り替えて保存条件を適用し、AI全体を無効化して再試行 | 有効時は現在のレイヤーで再検索。無効時のAI適用は拒否し、既存の手動version 1機能は維持 |

さらに、旧クライアントのprotocol 1へ新操作が返らないこと、version指定なしの旧一覧がversion 1だけを返し件数・ページングも一致すること、保存定義に作成・削除等を混入させた直接要求を拒否することを模擬APIと結合テストで確認する。これらはLLMの文章解釈と独立したサーバー側の要件である。

## 実データに基づく入力例の評価

以下はLLMの推論とは独立して確認する。候補の取得・表示・挿入だけでは実サービスを呼ばない。送信後の解釈を確認する場合だけ、通常のLLM利用料が発生する。上記の架空データを使い、他者データ・不正値・空レイヤーも別ケースとして用意する。

| ID | 操作・状態 | 期待する結果 |
| --- | --- | --- |
| Q44 | チャットを開いて入力例を確認 | 最大3件。現在の所有レイヤーの最新登録・投稿時の型・実在する値を使う。古い5年や他者の値、未使用の選択肢を根拠にしない。候補API `/ai/suggestions` 自体はLLM・DNS・キー復号を行わない |
| Q45 | 空欄でTab、またはPC・モバイルの「例を入力」 | 表示中の候補文だけを入力し、送信・地図反映は行わない。消して空欄へ戻すと次の例を表示する |
| Q46 | 入力済み・IME変換中・Shift＋Tab・候補なしでTab | 下書きを上書きせず、通常の入力・フォーカス移動を維持。一般例は「例を入力」から入力できる |
| Q47 | 候補の応答を遅延させ、その間に入力・音声認識・閉じる・対象変更 | 取得で全画面スピナーを出さず、入力と送信を妨げない。入力文を上書きせず、古い範囲・閉じた画面へ遅延応答を反映しない |
| Q48 | 60秒以内に開き直す、地物やフォームを連続更新、期限後に開き直す | 同じ条件ではキャッシュを再利用。更新通知の取得をまとめ、候補だけを失効させて会話・undo・適用済み条件を維持。期限切れは一般例へ戻し、再取得で外部更新にも追随する |
| Q49 | 空データ・上限超過・取得失敗・候補APIのない旧サーバー | 一般例へ戻り、通常チャットを利用できる。投稿時項目定義が多い・大きいフォームもJSONをアプリへ展開する前に除外し、従来の手動検索は維持する。候補取得の回数制限だけで通常チャットの送信枠を消費しない。SQLiteの取得期限・SQL中断後に接続設定が復元され、次の通常検索を妨げない |
| Q50 | AI無効化・設定変更・他者レイヤー・別アカウントを直接要求 | 認証・所有範囲・設定版を検証し、候補文を漏らさない。取得後の設定変更も再検証する。候補はブラウザーへ永続保存せず、HTMLとして解釈しない |

## SQLiteと起動環境の追加確認

次の項目はLLMの日本語解釈とは別に、一時DBや模擬APIによる自動試験と、利用者による端末確認に分けて実施する。

- 新規・更新DBの起動時マイグレーション26・27、既存データ保持、同時保存の409競合、同じ操作IDの二重確定防止を確認する。
- 設定版・操作IDがAPIでUUID文字列のまま返り、DBではTEXT、設定JSONはTEXT、暗号文はBLOBで保存されることを確認する。既存の非UUID文字列ユーザーIDも認証・所有範囲・アカウント照合を維持する。
- 初回起動でJSONの `ai_encryption_key` が生成・保存され、再起動後も同じ鍵でLLM・音声の保存済みAPIキーを使えることを確認する。従来の `AI_ENCRYPTION_KEY` は優先され、JSONに鍵がなければ同じ値を保存すること、既存JSON鍵は上書きしないことも確認する。
- 不正な鍵、全鍵不在で暗号化APIキーが残る状態では新しい鍵を生成せず拒否すること、接続先や暗号文の改変を拒否することを確認する。読み取り専用のタイルCLIでJSON・バックアップ・DBを変更しないことも確認する。鍵の紛失試験はコピーした検証DBだけで行う。
- 入力例の5秒期限、SQLiteのSQL中断後の接続再利用、定義の件数・容量予算、0・false・大きな十進数の候補と通常検索の意味が一致することを確認する。
- Tauriのlocalhost画面とサーバー単体モードのブラウザー画面を区別して、マイク許可・実形式・停止・文字入力への復帰を確認する。LANの通常HTTPホストでは録音を利用せず、HTTPSかlocalhostで確認する。

自動試験のコマンドと一時DBの扱いは [検証手順](AI_ASSISTANT.md#検証手順) を参照する。実アプリ起動・ブラウザー・実LLMの評価は利用者が実施し、未実施のケースを成功件数へ含めない。

## 記録

SQLite版のアプリバージョン、Tauri／ブラウザー・OS・HTTPS／localhostの区分、接続方式・モデル名・実施日、ケースID、初回／聞き返し後の成否、生成された条件、APIで確定した対象名・件数、反映完了、応答秒数、サービス側の利用量を記録する。作成保存では操作ID、確認前の未作成、確定・結果照会の状態、実際の作成件数も記録する。APIキーや実業務データを記録しない。失敗は『条件解釈』『許可外の誤分類・誤実行』『API失敗』『画面反映』『確認・永続変更』『保存互換性』『音声認識』に分け、モデル変更時にも同じケースを再評価する。

音声ではQ03・Q06・Q15を読み上げ、認識文章の確認・編集後に送信する。日本語の年・小数・施設名、権限拒否、無音、録音停止、画面非表示、認識失敗から文字入力へ戻れることを実端末で確認する。
