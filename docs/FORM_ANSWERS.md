# フォーム回答の登録・検索・編集

PostgreSQL版・SQLite版の両方で、所有者の入力と外部公開フォームからの回答を検索できます。本文・図形メモへの自由入力は分析対象になりません。分析の中心は検索・絞り込み・地図確認・CSV出力で、合計・平均などの集計画面はありません。

## 所有者が新しい回答を登録する

1. 地図オブジェクト一覧の対象名を押して編集画面を開きます。
2. 未設定の場合は「入力フォーム設定」で項目を設定します。
3. 「フォームで回答を登録」を押し、入力して「回答を保存」を押します。

保存済みフォームに項目があれば、外部公開が無効でも利用できます。登録ごとに新しい回答履歴が増え、回答内容をマーカー本文・図形メモにも追記します。既存回答の修正は後述の「編集」から行ってください。

## 回答一覧を開く

ツールバーの「共通フォーム作成・管理」→「フォームからの回答一覧と分析」を選びます。共通フォームの「一覧」にある「回答一覧」からは、そのフォームを選択した状態で開けます。PC・モバイルとも利用できます。

広い画面では、左右に余白を残してモーダルを広げ、テーブルに残りの縦幅を割り当てます。詳細列は操作ボタンに合わせた幅で中央に配置します。絞り込み条件が長い場合は一覧全体をスクロールでき、狭い画面ではカード表示になります。

「すべての回答」は全履歴、「対象ごとの最新回答」は対象・フォームごとの最新1件です。最新1件を選んでから条件を適用するため、最新回答が条件に合わなくても過去の一致回答で補いません。投稿日時が基準で、過去回答を編集しても最新の順序は変わりません。

## 条件を編集して反映する

1. 「絞り込み」を開き、「共通フォームを選択」、適用元の版、対象種別、レイヤを指定します。広い画面では4項目が横一列に並びます。
2. 適用元の版は共通フォームを選ぶと指定できます。対象名・回答日時の入力欄と「詳しい条件」の展開はありません。
3. 回答内容で検索する場合は共通フォームを選び、「条件を追加」で項目と比較条件を指定します。複数条件はすべてに一致する回答が対象です。
4. 青色の「絞り込む」または「変更を反映」を押します。条件を編集しただけでは表示中の結果やCSVに反映されません。
5. 「表示する項目」で一覧に表示する回答項目を選びます。「詳細を見る」では投稿時のフォーム定義に沿った回答を確認できます。

| 状態 | 意味 |
|---|---|
| 未入力 | 投稿時に項目は存在したものの、値が未入力です |
| 項目なし | 投稿時のフォームにその項目がありません。後から追加した項目などが該当します |
| 0 | 数値の回答です。未入力ではありません |
| false（いいえ） | チェックボックスの回答です。未入力とは区別します |

フォームの版や項目の種類が異なる場合は、項目名だけで同じ回答と判断せず、詳細の投稿時定義を確認してください。投稿時の定義を持たない旧回答には、項目IDなどで表示する場合があります。

## 地図で確認・CSV・印刷

「地図で確認」で一覧の全ページの該当対象を表示します。同じ対象は重複させず、10,000件を超える対象も地図・絞り込み・色分けで扱えます。地図では回答条件、対象名、レイヤなどで追加の絞り込みができます。回答条件を変更したら「絞り込み」で反映し、「地図条件を解除」で一覧から渡した範囲に戻します。

開いた直後は、トップ地図で表示していた中心位置とズームを引き継ぎます。「表示範囲の移動」で該当対象全体へ移動できます。トップ地図の位置を取得できない場合は、最初から対象全体を表示します。回答地図で移動・拡大縮小しても、トップ地図の保存位置は変更しません。

表示位置・形状・名前などは現在の情報で、回答時点の地図を復元するものではありません。ポップアップの「フォームからの回答」は対象に保存された全回答の修正後の内容を表示し、検索に一致した回答だけには限定しません。

| 操作 | PC | モバイル |
|---|---|---|
| 一覧の「CSV出力」 | 対応 | 対応 |
| 回答地図での追加絞り込み | 対応 | 対応 |
| 回答地図での条件による色分け | 対応 | 対応 |
| 回答地図で絞り込んだ対象の「CSV出力」 | 対応 | 非対応 |
| 回答地図の「地図を印刷」・PDF出力 | 対応 | 非対応 |

一覧CSVは反映済み条件の全ページが対象です。PCの回答地図CSVは、その地図で絞り込んだ対象を出力します。CSVは最大10,000回答・回答項目200種類です。上限を超える場合は条件を絞ってください。

印刷用スナップショットは32MiBまでです。地図に表示できる対象でも、形状や本文が大きい場合は印刷対象を絞ってください。項目候補の完全定義10,000件・統合後200項目の上限と、各APIの要求容量の制限も維持しています。地図の対象数、CSVの回答数、項目定義数、印刷容量は別の基準です。

モバイルの回答確認用地図には「機能を表示／機能を非表示」があり、地図上の操作部の表示を切り替えられます。PCの印刷手順は[地図印刷](MAP_PRINTING.md)を参照してください。

### 10,000対象制限の撤廃と実データ検証

2026-10-29、SQLite版の実データ（22,537回答・19,776対象、すべて図形）を整合したバックアップへ複製し、読み取り専用で検証した。元DB・設定は変更しない。Release版の実際の地図・絞り込み・印刷・CSV上限確認APIと、本番ビルドしたPC／モバイルのAnswerMapModal・地図モジュールを組み合わせる。PostgreSQL版は一時DBの20,000対象の結合テストで検証し、実アプリDBでの性能は計測していない。

Chrome 156.0.8078.48で、PCは1280×800、モバイルは390×844・CPU4倍制限のエミュレーションを使用した。実端末での検証ではない。全対象の保持、移動・拡大縮小、絞り込み・解除、3分類の色分け・再評価・解除、ポップアップ、3回の開閉を確認し、実行エラーはなかった。実DBで選んだ項目の分類内訳は入力あり19,776件・未入力0件・項目なし0件だった。対象数が減る条件は、20,000対象から10,000対象へ絞る両バックエンドの合成テストでも確認した。各閉鎖後のiframeと地図ランタイムの弱参照は0件になった。背景タイル・アイコン・画像はローカルの代替画像を使用し、実認証と外部通信は含めない。通常編集地図とPinia原本ストアは同時に生成しないため、アプリ全体や実端末のメモリー保証には使わない。

絞り込み用の項目候補取得にも、同じ項目配列の代表回答を選んでから展開する処理を適用した。フォームの範囲を先に限定し、地図条件用の日時・回答ID降順／対象種別昇順、現在の定義優先、ラベル・選択肢・項目順・旧回答の扱いを維持する。完全定義10,000件・統合後200項目の判定も変更しない。旧新SQLの結果・順序・境界値は両バックエンドで比較する。

次は、対象数制限だけを外した候補と、項目候補の重複展開も改善した最終版の各1回の通し計測（秒）。旧製品はこの対象数を開けなかったため、制限撤廃自体の高速化率を表す比較ではない。HTTP・DB・JSON・Vue・iframe描画・操作待ちを含み、中央値でもバックエンド単独の時間でもない。

| 操作 | PC（候補→最終） | モバイル表示（候補→最終） |
|---|---:|---:|
| 項目取得と「入力あり」の絞り込み | 8.17→5.74 | 9.05→6.43 |
| 項目取得と3分類の色分け | 11.70→8.49 | 12.89→9.68 |
| 色分け中の絞り込み変更 | 15.70→11.91 | 17.66→13.29 |

最終版の初回表示はPC約5.21秒・モバイル表示約7.95秒だった。HTMLは約72.6MBあり、初期の全文取得・解析負荷は残る。地図が保持する19,776対象と、表示範囲・縮尺に従って生成する描画オブジェクトは別で、初期生成は83図形だった。開閉後のメモリー値はGC後のJSヒープだけで、ブラウザー全体の使用量ではない。

CSVは22,537回答の要求を既存の10,000回答上限で拒否した。全対象の印刷スナップショットは約72.6MBのため32MiB上限で拒否し、凡例で1,000対象に絞った印刷では1,000図形すべての生成を確認した。印刷用図形の準備は約555msだったが、代替リソースを使う計測では1レイヤの読込状態が残り、印刷ボタンは既存の30秒後の案内「現在の表示で印刷」に移行した。この待ち時間は図形生成時間と区別する。図形の読込失敗・処理残りはなかった。

地図対象数の判定は両バックエンド、PC・モバイル、地図の絞り込み・色分け、印刷データの検証から削除した。印刷対象の照合は集合を使い、対象数が多い場合の繰り返し走査も避ける。所有権・対象種別・ID・重複・件数整合性は引き続き検証する。要求容量1MiBは維持し、今回の対象ID転送は約890KBだった。対象数制限の撤廃は、データ容量が無制限になることを意味しない。

関連RustテストはPostgreSQL98件・SQLite115件、診断例のテスト1件が通過した。両版のPC・モバイル・地図スクリプトの関連テスト、型チェック、本番ビルドも通過した。DBマイグレーションは追加していない。

再現時は、SQLiteのバックアップ機能で整合した複製をSQLite版の `target/` 配下へ作成し、次をSQLite版ルートで実行する。診断サーバーはloopbackに限定し、起動・マイグレーションを行わない。生成するHTML・条件・manifestには実データが含まれるため、公開用の計測結果へ含めない。

```powershell

cargo run --release --locked --offline --jobs 1 --example profile_answer_map -- --database target/PRIVATE_COPY.sqlite --output-directory target/private-answer-map --serve --port 0
```

表示されたポートを使い、次をPostgreSQL版ルートで実行する。SQLite版ルートで実行する場合は `--manifest=target/private-answer-map/manifest.json` とする。PlaywrightとChromeは事前に用意する。

停止後に診断サーバーは生成した実データファイルを削除する。DB複製は使用者が削除する。今回の調査用複製も削除済み。[計測JSON（前後各試行・条件・ソースハッシュ・検証結果）](performance/answer-map-target-limit-removal.json)には、件数・時間・サイズなどの集計値だけを保存する。

### 回答地図の初回表示の調査と改善計画

2026-10-29、同じSQLite実データ（22,537回答・19,776図形）の整合した複製を読み取り専用で調査した。製品の取得・描画処理は変更せず、診断例と計測ビルドにだけ観測を追加した。PostgreSQL版は対応するコードを確認したが、実DBの性能は未計測である。

#### サーバー側の内訳

Release版の実際の `answer_map_handler` を、事前の原本読込と1回のウォームアップ後に3回順次呼び出した。時刻・検索条件を固定し、別のビルドやテストは同時に実行していない。各項目の中央値は次のとおり。

| 区間 | 時間 |
|---|---:|
| ハンドラー全体（送信を除く） | 2,745.5ms |
| SQLxで観測した取得・行変換など | 1,941.1ms |
| テンプレート生成 | 200.5ms |
| 上記テンプレート内のHTML安全化JSON生成 | 173.5ms |
| 観測済みSQL・テンプレート以外の残り | 603.0ms |

SQLxの時間はSQL実行だけでなく取得・行変換などを含み得る。残りは本文の組立て、Contextへの変換、待機、解放などが混在し、純CPU時間ではない。JSON生成はテンプレート生成の内数であり、加算しない。中央値も区間ごとに算出している。

取得のうち、図形19,776件が約722.9ms、ポップアップ用の全回答22,537件が約939.1ms、件数集計が約197.3msだった。ポップアップの取得は、その用途で参照しない `submitted_values`・`form_snapshot` もJSONとして復元している。この2列の保存JSONは合計91,065,110 bytesだった。これはDB列の直列化サイズであり、通信量やメモリー使用量ではない。

生成HTMLは72,597,480 bytes。HTML安全化後の図形データが44,040,907 bytes、ポップアップの投影が27,645,776 bytesで大半を占める。図形のメモとポップアップの本文に重複があるが、自由入力・回答の配置や曖昧な旧本文を維持するため、単純な削除・連結では置き換えない。

#### ブラウザー側の内訳

本番ビルドした実コンポーネントと地図モジュールを使い、Chrome 156.0.8078.48でPC・モバイル各3回を計測した。PCは1280×800、モバイルは390×844・CPU4倍制限のエミュレーションで、実端末ではない。各試行は新規context／pageで、バックエンド・OSキャッシュとChromeプロセスは再利用する。初回のディスクキャッシュを空にした測定ではない。

| 区間・到達時点 | PC | モバイル表示 |
|---|---:|---:|
| 開く→読み込み表示の解除 | 4,025.3ms | 7,124.8ms |
| 開く→候補取得・図形生成・待機を含む既存計測の完了 | 4,756.7ms | 8,159.7ms |
| 大きなbootstrapスクリプトの直前→直後 | 661.3ms | 3,126.6ms |
| 地図runtimeの同期初期化 | 73.6ms | 340.0ms |
| 上記初期化内の図形原本登録 | 17.3ms | 55.5ms |
| ready受信→初期の項目候補取得完了 | 574.5ms | 712.8ms |

bootstrapは `JSON.parse` ではなく、HTML内の巨大なJavaScriptオブジェクトリテラルである。別scriptの前後へ計測点を置いた区間は、残りの受信・HTML解析・コンパイル・評価と重なり、純粋なJavaScript実行時間ではない。CDPの集計ではコンパイル時間がPC約0.30秒・モバイル表示約1.53秒だったが、これも他の区間と加算しない。

初期生成は83図形で、原本19,776件・処理残り0件を確認した。ready通知は論理対象の集計後に送られ、すべての描画完了や実際のpaint完了を示すものではない。読み込み表示解除後のdouble-rAF到達はPC約4.09秒・モバイル表示約7.43秒だった。背景タイル・アイコン・画像は代替画像を使い、実認証と外部タイル通信は含めない。通常編集地図とPinia原本ストアは同時に生成せず、この測定では親の位置を継承できない場合の全体表示を使用した。

診断proxyはHTML全文を受信して書き換えるため、応答ヘッダー受信後の本文回収・UTF-8変換・書換えなどに約0.43〜0.46秒の計測専用負荷がある。各段階を別に記録し、製品バックエンドの時間と区別する。上の到達時間はこの負荷も含み、アプリ全体・実端末・実通信の表示時間を保証する値ではない。6試行すべてでエラーなし、閉鎖後のiframe・runtime弱参照は0件だった。

#### 改善を進める順序

1. **ポップアップ専用の取得列を絞る。** `id`・`target_id`・`rendered_markdown` の軽量な行型を使い、編集用の回答型は維持する。本文の組立ては必要最小限の情報を受け取れるようにし、不要な本文cloneも確認する。同一トランザクション、その対象の全回答、順序、旧本文の対応判定を変えずに、最初の改善単位として実装・再計測する。
2. **大きなデータを実行スクリプトから分ける案を比較する。** 同じ認証付きnative POST・同じ1回の応答の中で、HTML安全化した `application/json` のbootstrapを一度だけ `JSON.parse` する方式を試作する。初期化後に元テキストのDOMを解放し、現行のbootstrap値・原本・ポップアップを維持する。PC／モバイルの実モジュールで解析時間とメモリーを比較し、効果と互換性を確認してから採用する。JSON化だけで通信量が減るとは扱わない。
3. **全文スナップショットを維持した伝送上の重複排除を検討する。** 通常本文とポップアップの文字列を共通参照にする方式、または検証済みの本文区間を使う方式を別に試作する。partsの順序・繰り返し文字列・絵文字の位置・未対応の旧本文を扱えない場合は従来の全文へ戻す。再構築後の通常本文・自由入力・全回答が完全一致することを条件とし、開いた後の最新DB取得へ置き換えない。
4. **再計測後に残った初期化・候補取得を扱う。** 本文組立て／Context変換の残りや初期の候補要求をさらに分離する。今回の図形原本登録・runtime生成は主要な遅延区間より小さいため、前段の改善後に優先順位を判断する。

各段階で、全ページの対象集合、所有者、`latest` 決定後の条件適用と `as_of`、現在の形状・名称、トップ地図の中心・ズーム継承を維持する。ポップアップの通常／自由入力／全回答の切替、曖昧な旧本文の扱い、401再送、閉じた後・再表示後の古い応答破棄、検索・色分け・CSV・印刷対象も変えない。印刷は確定済みデータだけを受け取り、32MiBは再構築後の内容へ適用する。CSV10,000回答、完全定義10,000件・統合200項目、要求容量1MiBも維持する。API追加・キャッシュ追加・DBマイグレーションは現段階では計画しない。

回帰検証には、両バックエンドの回答地図・ポップアップ投影テスト、PC／モバイルの位置継承・401・遅延応答テスト、地図側の本文切替・絞り込み・印刷スナップショットを使う。特に取得列変更前後の投影全文、Unicode・HTML安全化、再表示・失敗時の整合性、印刷データの完全性を比較する。速度の固定しきい値は機能テストへ入れず、同じ実データと条件で前後を各3回計測する。この調査時点では性能改善本体は未実装だった。第1段階の取得列削減の結果を次節へ追記した。

今回の全19,776対象では、通常本文が同じ対象の `free_text + managed_markdown` と全文一致した。通常本文のHTML安全化JSONトークンは合計25,589,071 bytesある。例として対象ごとの47bytesの参照と33bytesの形式識別情報へ置き換える計算では、HTMLは72,597,521→47,937,955 bytes、約24.7MB・34.0%減となる。これは未採用の表現によるデータ量の試算で、最終形式の付帯情報・復元処理・速度・メモリー効果は未検証である。

次は以下を満たす小さな試作で比較する。

- サーバーが対象ごとに文字列の元の通常本文との厳密な全文一致を確認し、成功分かつ元のJSONより小さくなるものだけ決められた順序の参照にする。不一致・非文字列・memo欠落は従来のデータを残し、`sync_required`・旧本文の曖昧さ・回答順序・保存済みpartsを変更しない。単純な連結を全データへ仮定しない。

#### 参照形式と全文の復元

HTML生成時だけ、通常本文が同じ対象の `free_text + managed_markdown` と厳密に全文一致し、参照情報を含めても小さくなる場合に、その `marker.detail`／`shape.geojson.properties.memo` を省く。専用のトップレベル情報 `normalBodyReferences = { version: 1, markers: [...], shapes: [...] }` に対象IDを持つため、利用者のGeoJSONや文字列に似た値が保存されていても混同しない。

### 地図で色分けする

「地図で色分け」はモーダルを開いた際に展開されます。共通フォーム、分類名、色、回答条件を設定して「色分け実行」を押します。分類内の条件はANDで判定し、複数の分類に一致する対象は上の分類を優先します。一致しない対象は元の色を維持します。「色分け解除」で元のアイコン・図形色に戻ります。

一覧条件、反映済みの地図条件、その分類の条件を同じ回答へ適用します。最新回答／履歴の選び方も一覧と同じです。各分類の判定で使う回答条件は合計20件までです。絞り込みで共通フォームを指定した場合は、色分けにも同じフォームを使用します。

条件を編集中の状態は地図へ反映されません。色分け適用後に絞り込みを変更した場合は、適用済みの分類を再評価します。通信に失敗した場合は直前の表示を維持します。適用・解除で地図の位置やズームを変えず、通常地図や保存済みのスタイルも変更しません。色分けだけではCSVの対象や列を変更しません。

マーカーがクラスターにまとまっている間は、通常と同じ件数に応じたスタイルで表示します。拡大して個々のマーカーを表示すると、それぞれの分類色を確認できます。

PCで色分けした地図を印刷すると、印刷開始時点の分類結果と、分類ごとの凡例を引き継ぎます。印刷画面では分類単位の表示切替、文字サイズ変更、凡例枠のサイズ変更ができます。詳しくは[地図印刷](MAP_PRINTING.md#色分けした回答地図の凡例)を参照してください。

### 検索条件を保存・呼び出す（PostgreSQL版）

「地図上で絞り込み」「地図で色分け」のそれぞれの「検索条件を保存」を押すと、入力中の条件に名前を付けて保存できます。名前は必須で100文字以内です。「閉じる」では保存しません。同名でも上書きせず、別の保存条件として登録します。条件を保存するだけでは、地図に反映しません。

PCでは「CSV出力」の隣、モバイルでは回答地図のヘッダーにある「保存した検索条件」から、自分が保存した条件を一覧で確認できます。「呼び出し」は該当する入力欄だけを復元します。内容を確認し、従来の「絞り込み実行」「色分け実行」で地図へ反映してください。

保存するのは共通フォーム、項目・比較方法・値、色分けの分類名・色・順序です。検索結果・対象ID・地図位置・印刷設定は保存しません。呼び出した画面の一覧条件・対象範囲・最新／履歴モードをそのまま使います。フォームや項目が使えなくなった場合、条件を黙って省略せず案内し、現在の入力を維持します。

「削除」を押すと確認メッセージを表示し、確認の「削除」で保存条件を削除します。「閉じる」では削除しません。保存条件を削除しても、呼び出し済みの入力や適用済みの地図は変わりません。保存条件の更新・共有はなく、作成したアカウントだけが取得・削除できます。

導入時は `migrations/20261025120000_answer_map_saved_conditions.sql` を通常の `sqlx migrate run` で適用し、APIとPC・モバイルのアセットを更新してください。保存条件用テーブルを追加し、既存の回答・共通フォームは変更しません。

APIは認証必須の GET/POST `/form-answers/map-presets`、DELETE `/form-answers/map-presets/{id}` です。一覧は `page`（初期値1）・`page_size`（初期値20、最大100）で取得します。所有者は認証情報から決定し、他人のIDを指定した削除は未登録のIDと同じ404を返します。

投稿時の定義がない旧回答は閲覧のみです。旧本文との対応が曖昧な場合は、元の本文と回答部分を確認し、残す自由入力を指定してから保存します。同時編集などで競合した場合は、画面の案内に従って再読み込みし、最新内容を確認してから修正し直してください。

## 自由入力・回答部分と削除

通常のオブジェクト編集の本文欄と、地図上の図形編集のメモ欄は自由入力部分を編集します。フォーム由来の内容は確認できますが、修正は回答一覧から行います。レイヤの[自由記述制限](LAYERS_AND_MARKERS.md#自由記述の制限)がONの場合は、フォームで登録・編集してください。

## 回答一覧の取得負荷対策

初回表示・再表示では、項目候補の取得（`/form-answers/options`）と先頭50件の検索（`/form-answers/search`）を並行して開始する。呼び出し回数はそれぞれ1回のままで、回答と列定義が両方揃ってから一覧へ反映する。片方が失敗した場合は部分的な一覧を表示せず、エラーを保持する。閉じた後や再表示前の取得結果は引き続き無視する。ページ移動・通常の検索・保存後の再検索は既存の取得方法を維持する。

PostgreSQL・SQLiteとも、履歴表示（`history`／モード未指定）では最新回答用の順位計算を行わず、対象範囲から直接条件を適用する。最新回答表示（`latest`）では、従来どおり対象・フォームごとの最新1件を選んだ後に版・期間・回答条件を適用する。件数集計とページ取得、項目候補、CSV・回答地図で共用する検索処理へ適用し、所有者・検索条件・`as_of`・順序・カーソル・各上限を維持する。APIの入出力・DBスキーマ・キャッシュの寿命は変更しない。

フォーム候補は、未削除の共通フォームに加え、所有するマーカー・図形の回答から参照されている削除済みフォームを返す。SQLite版では参照中のフォームIDを所有回答から一度で集め、削除済みフォームごとに全対象・回答の存在確認を繰り返さない。他アカウントのフォームや他アカウントの対象にしか回答がない削除済みフォームは候補へ含めず、候補の内容・順序は維持する。フォームを削除しても回答履歴を保持する仕様は変更しない。

### 日時解析と項目定義の集約

SQLiteの回答用読み取りトランザクションは、日時照合で解析した結果を再利用する。読み取り開始ごとに独立したキャッシュへ交換し、接続に残るキャッシュは最大512文字列・キー合計32 KiB・1文字列256 bytesまでに制限する。解析できない値も結果を保持し、上限を超える値は従来どおり解析する。256比較ごとに再利用率を確認し、片方以上の日時を再利用した比較が1/4未満なら、その読み取りでは以後のキャッシュ照会を止めて従来比較へ戻る。UTCオフセット、混在書式、細かい時刻差、解析失敗時の文字列比較を維持する。回答原本や検索結果のキャッシュではなく、書き込み側の日時照合は変更しない。

フォーム・対象を指定した項目候補取得では、同一の項目配列を持つ回答のうち、日時・回答ID・対象種別の降順で最新の1件を選んでから項目を展開する。その後の完全定義ごとの重複排除、表示順、ラベル・選択肢の統合、完全定義10,000件・統合後200項目の上限は維持する。フォームIDや版番号だけではまとめず、配列内の順番も含めて比較する。定義なしの旧回答の項目は元の回答集合から集約する。

PostgreSQLは既存どおりJSONBの等価性で比較する。SQLiteは配列型だけをJSON文字列の完全一致でまとめ、展開には元のスナップショットを使用する。配列以外・JSON null・項目欠損の扱いを変更しない。これらはCSV・回答地図・分析・保存条件からも共用する処理であり、API・DBスキーマ・50件ページング・検索対象を変更しない。全体一覧の初回候補取得では項目の集約を行わないため、項目配列の代表化はその処理時間へ影響しない。

SQLiteの回答検索は、件数集計とページ候補の選定では表示用のレイヤ・共通フォーム結合を行わず、回答値・スナップショットも回答条件で必要な場合だけ参照する。共通の検索条件組立てで候補の種別付き回答IDを確定してから、同じ読み取りトランザクション内で候補だけの全文・表示用属性を取得する。既定は50件と次ページ確認用1件で、APIの既存の上限100件も維持する。最新回答を決めてから版・期間・回答条件を適用する順序、所有者、カーソル、件数とページの同一スナップショットを変更しない。PostgreSQLはこの検索専用投影へ変更していない。
