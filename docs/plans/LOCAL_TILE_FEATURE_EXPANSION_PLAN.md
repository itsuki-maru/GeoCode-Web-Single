# ローカル地図の建物・土地被覆・標高地形への拡張計画

作成日：2026-11-12。状態：F0〜F9の実装・自動回帰・単体exe作成を完了。[実装・検証記録](LOCAL_TILE_FEATURE_EXPANSION_PROGRESS.md)を参照。実地域での全国取り込み・アプリの操作確認は利用者が実施する。調査基準はcommit `9196f72`で、計画作成前の作業ツリーに未コミット変更はなかった。

利用者の回答により、**建物・水域・森林などの面地物と、山の陰影・等高線を初期対応に含める**。本計画のF0〜F9を初期対応の範囲とし、陰影・等高線を後続対応へ切り離さない。

計画作成ではソースと一次資料だけを確認した。実設定JSON、本体DB、タイル管理DB、完成DB、PNG、ジョブ履歴、実行中プロセスは操作していない。実装・ビルド・取り込みも行っていない。

## 1. 到達点と維持する制約

GeoCode-Web-Single本体のCLIでPBF・標高・海陸データを取り込み、本体が通常のXYZラスタタイルを生成・配信する。別のタイルサーバ、実行時のオンライン取得、外部のGIS変換コマンドは必須にしない。

- `src_frontend/`と`src/templates/`を変更せず、PostgreSQL版とのフロント互換性を維持する。
- 管理はCLIだけで行う。SQLite版専用の管理画面・HTTP管理APIを追加しない。
- 表示には既存の共通背景定義、`kind=raster`と`/local-tiles/<dataset_id>/<render_id>/{z}/{x}/{y}.png`を使う。地物・地形はバックエンドで1枚のPNGへ合成する。
- 本体の`migrations/`、共通テーブル設計、既存の独立タイル管理DBのスキーマ1を維持する。
- 既存道路DBを更新せず、新機能用の別完成DBを作る。旧dataset ID、render ID、URL、PNG、履歴、再開情報を維持する。
- コメント・整形・診断変更で世代を変えない、直前の[描画世代識別の方針](LOCAL_TILE_RENDER_IDENTITY_PLAN.md)を継続する。
- コードコメント・運用文書は日本語で記述する。実アプリの起動確認、インストール、Gitコミットは利用者が実施する。

## 2. 調査結果

| 現在の実装 | 拡張への影響 |
| --- | --- |
| `src/tilegen/pbf.rs`の公開地物はNode/Wayだけで、Relationを読み捨てる | 中庭付き建物、島のある湖、分割された森林等のmultipolygonに対応できない |
| `import.rs`は道路Way抽出と必要Node解決の2走査 | 建物・土地被覆・水域の属性と必要Nodeは現行完成DBに残っていない。元PBFからの新規取り込みが必要 |
| `store.rs`はschema=1/geometry=1、道路属性、単一折れ線、Way IDの一意性を前提とする | 複数外周・穴・Relation ID・DEMを保存する新形式が必要。版定数だけの置き換えでは旧DBを開けなくなる |
| `renderer.rs`と`geometry.rs`は道路線の描画・切り抜きが中心 | 面の塗り、穴、巨大面の切り抜き、地形合成を別に追加する必要がある |
| `Style`、`Dataset`、実行ワーカーは1データセットにつき1つの既定描画契約 | 初期はこの構造を維持し、形式ごとに道路用・標準地図用の契約を選ぶ |
| `identity.rs`、`profile.rs`、実行認定は道路契約を前提とする | 旧契約を固定したまま、新契約とその数値演算・依存構成の認定を追加する |

OSMの建物外形や土地被覆はPBFから取得できる。一方、OSMの`ele=*`は個別地物の標高であり、連続した標高格子の代わりにはならない。陰影・等高線には別途DEMを入力する。[建物の仕様](https://wiki.openstreetmap.org/wiki/Key:building)、[複合面の仕様](https://wiki.openstreetmap.org/wiki/Relation:multipolygon)、[OSMの標高情報](https://wiki.openstreetmap.org/wiki/Key:ele)

## 3. 初期対応の地物とデータ

| 分類 | 初期の対象案 | 主な表示方法 |
| --- | --- | --- |
| 道路 | 現行の道路分類・橋・トンネル・layer | 現行道路の線描画を継承し、新標準地図の配色・合成順へ組み込む |
| 建物 | `building=*`の有効な面。`building=no`等は除外 | 高ズームで2Dの塗りと輪郭線。中庭も保持する |
| 土地被覆・土地利用 | 森林、草地、公園、農地、住宅地・商業地・工業地、砂地・裸地等 | 分類別の薄い面色。低ズームでは投影面積で細部を抑制する |
| 内陸水域 | 湖・池・貯水池・河川面、対応するmultipolygon | 水色の面。島を穴として保持する |
| 水路・鉄道 | 主な`waterway=*`、運行中の鉄道線 | ズームと分類に応じた線。橋・トンネルとの重なりを規定する |
| 海と陸 | OSM由来の処理済み陸域ポリゴン | 海色の下地に陸域を描画。PBFの地域切り出し境界を海岸として閉じない |
| 陰影 | 国土地理院のDEM | 地表の上へ弱く合成。水面・道路・建物の可読性を保つ |
| 等高線 | 同じ正規化DEMから生成 | 初期案は20m間隔・100mごとの強調線。低ズームでは間引く |

対象タグの許可表、競合時の優先順位、最小表示ズーム、面積閾値はF0で固定する。`area=no`、未閉鎖Way、`building:part`のみの面、廃止・工事中の地物、未知タグをどの分類へ含めるかも明記する。

地名・建物名・POI・標高数値のラベル、3D建物、地質図、航法用途の水深、OSM差分による自動更新、一般GeoTIFFの全面対応、任意スタイルの切替は後続対応とする。初期の等高線は線と強調線までを含み、文字配置・日本語フォントの仕組みは追加しない。

### 標高入力

日本向けの初期必須形式は、国土地理院の基盤地図情報DEMのFGD-GML（ZIP/XML）とする。全国の土台はDEM10B、必要地域の細部は対応する5mデータで補う。公式情報ではDEM10Bは全国整備、細密なDEMは整備地域が異なるため、未収録の範囲も扱う。[公式ヘルプ](https://service.gsi.go.jp/kiban/app/help/)、[公式FAQ](https://service.gsi.go.jp/kiban/app/faq/)

現在の配布仕様にはJGD2024が含まれる。対応するJGD2011/JGD2024の地理座標を明示し、格子位置・軸順・標高基準・改定版を検査する。JGD2024への名称変更で水平座標値が一律に変わったとは扱わない。異なる標高基準を黙って混合・補正しない。[配布仕様5.3](https://service.gsi.go.jp/kiban/contents/screen/basismap/documents/FGD_DLFileSpecV5.3.pdf)、[日本の測地系](https://www.gsi.go.jp/sokuchikijun/datum-main)

データの取得は利用者が事前に行い、CLIへローカルファイルを指定する。国土地理院の認証情報を本体へ保存したり、表示要求からダウンロードしたりしない。対応するGML仕様版・CRSの組合せをF0で一覧化し、未知形式は理由を示して拒否する。

### 海陸入力

海岸線は一般の湖の閉じた面とは別に扱う。地域PBFの`natural=coastline`をそのまま閉鎖して海を塗る方式は採用しない。初期はOSM由来の処理済み陸域ポリゴンをローカルファイルから読み込み、本体内で対象範囲・ズーム向けに準備する。第一候補は公開データのWGS84 Shapefileで、初期の対応形式を限定する。[海岸線の仕様](https://wiki.openstreetmap.org/wiki/Tag:natural=coastline)、[処理済み陸域ポリゴン](https://osmdata.openstreetmap.de/data/land-polygons.html)

DEM欠損を海と判断しない。陸域マスク、PBF地物の外接矩形、DEM収録範囲を別情報として管理する。海陸入力がない構成では中立色の背景を使い、海を確定表示できないことをCLIへ出力する。

## 4. 保存構成と互換性

### 新完成DBへ必要な情報を閉じ込める

初期方式は、**新しいschema=2/geometry=2の完成SQLite DBに、OSMの線・面、正規化DEMチャンク、必要なDEM階層、生成済み等高線、海陸面、各入力のメタデータをまとめる**方式とする。

描画時に元PBF・GML・ZIP・Shapefileへアクセスしない。完成DBを登録した後は元データの保存先変更や削除で描画が変わらない。既存の道路完成DBとは別ファイルを作り、上書き・追記・内部マイグレーションをしない。

保存表は概念上、メタデータ、線地物、面地物・外周・穴・部品、各検索索引、DEMチャンク・欠損マスク・階層、等高線に分ける。DEMは固定格子キーで索引し、すべてを道路用RTreeへ押し込まない。巨大な1個のBLOBや、全日本を囲む密な標高配列は作らない。

この方式では、DEMや海陸データの追加・更新にも新完成DBの作成が必要になる。初期CLIはPBFを含む再取り込みとし、作業用DBと新旧完成DBの併存容量を見積もる。独立DEM資材・任意合成プロフィールへの分離は、更新頻度・実測容量を踏まえた後続課題とする。

### 旧道路形式を残す

- 旧1/1の検証・読み取り・道路描画と既定の`roads-v1`を維持し、2/2は別分岐で処理する。
- 既存の任意カバリング索引の有無も引き続き許容する。新形式の登録だけで旧DBを新形式へ要求し直さない。
- 形式1の既存ID計算と保存メタデータを変更しない。新形式を追加したこと自体で道路契約のhashを変えない。
- 新形式の既定スタイルは仮称`standard-terrain-v1`とする。初期は形式ごとに既定契約を1つとし、汎用`--style`や可変DEM合成を導入しない。
- 対応形式追加をhashへ含めず、実際に読む形式・描画構成だけで契約を決める。

### 管理DB・ジョブ

タイル管理DBはスキーマ1の既存テーブルと`info_json`・`request_json`を使う。ジョブ種別も`import`/`precompute`のまま維持する。`src/local_tiles/migrations/0001_catalog.sql`とそのチェックサム、本体の`migrations/`を変更しない。

新規取り込み要求へ、地物セット、DEM入力、海陸入力、面の欠損方針等を追加する。古いJSONで追加項目が欠けている場合は、必ず従来の道路取り込みとして解釈する。保存済みJSONを一括書き換えず、既存request IDの再送照合も維持する。

現行の再送・実行中要求の重複判定はJSON文字列の完全一致である。道路要求の追加項目は既定値ならシリアライズ対象外にし、旧フィールド順とJSON表現を維持する。request IDありの旧要求再送と、IDなしの実行中要求の重複判定を別々のfixtureで確認する。

`datasets prepare`は完成DBの形式から既定契約を作成する。事前生成再開は保存済みrender IDとmanifestを使い、既定契約の選び直しをしない。履歴の列挙だけで新世代を作らない。

### 保存先

生成物は既存設定を使い、設定項目を増やす必要はない。

| 対象 | 既定値 | 変更するJSON項目 |
| --- | --- | --- |
| タイル管理DB | `~/.geocode-web-single/tiles/catalog.sqlite` | `tile_catalog_database_path` |
| 新旧完成DB。新DBには標高・等高線も内包 | `~/.geocode-web-single/tiles/datasets` | `tile_dataset_path` |
| PNG・事前生成manifest | `~/.geocode-web-single/tiles/png` | `tile_cache_path` |
| PBF・DEM等の取り込み作業領域 | `~/.geocode-web-single/tiles/work` | `tile_work_path` |

設定は従来どおり`geocode-web-single.env.json`で変更できる。入力元ファイルはCLIで任意のディスクの絶対パスを指定する。完成DBの既存外部参照登録も維持する。

## 5. 取り込み・地形生成・描画

### PBFと面の構築

新形式のPBF取り込みは次の3走査を基本とする。既存道路形式の2走査は残す。

1. 対象multipolygon Relationとmember Way IDをstaging SQLiteへ保存する。
2. member Wayと、単独で対象となる線・面のWayを保存し、必要Node IDを収集する。
3. 必要Nodeの座標を解決し、線と面を構築する。

RelationがWayより後にある一般的な並びにも、逆順の入力にも対応する。全Node・全Wayをメモリ保持しない。新地物キーはOSM種別・OSM ID・描画用途を区別し、WayとRelationの同じ数値IDを衝突させない。

面は共有端点のNode IDでmemberを結合し、逆向き・順不同member、複数outer、innerの所属を扱う。Relationタグの優先、旧形式のouterタグ継承、空role、同一分類のmember面との重複抑制を規則化する。Relationに所属するという理由で、独立した道路線まで消さない。

未閉鎖・欠損member・自己交差・穴の所属不正・未対応の入れ子Relation等は理由と件数を記録する。欠損辺を直線で補完したり、欠損innerだけを落として塗り潰したりしない。初期は入れ子Relationの再帰展開を対象外とし、面全体のエラーまたは明示的なスキップにする。

道路の`--missing-nodes error|skip-way`は意味を変えない。面には別の方針、仮称`--invalid-areas error|skip-feature`を設ける。既定は`error`とし、スキップを選んだ場合も分類別の除外数・理由を終了結果に残す。

面用LODは線の簡略化をそのまま流用しない。穴の消失・自己交差・共有境界の隙間を検査し、不成立なら原形へ戻す。高ズーム建物の原形や共通LODを再利用し、全建物を全ズーム分複製しない。大きな面の分割・切り抜きも、穴と境界の対応を維持する。

日付変更線を跨ぐ面は、世界全体を覆う誤った面にしない。初期に対応する分割方式と、未対応の場合の明示拒否をF0で固定し、既存道路の世界端処理は変えない。

### DEMの取り込み

ZIP/XMLを上限付きで順次読み、格子の範囲・軸順・セル位置・配列方向・`startPoint`・省略された欠損を解釈する。無効値を標高0mへ変換せず、標高値・欠損・水面等の種別を区別して保存する。[配布仕様5.3](https://service.gsi.go.jp/kiban/contents/screen/basismap/documents/FGD_DLFileSpecV5.3.pdf)

地表面・表層面・海水面・内水面・海水底面・内水底面・その他の採用可否をF0で固定する。水底を陸上地形の陰影・等高線へ誤採用しない。DEM入力を明示したのに有効な対象セルが1つもない場合は、地形付きの成功として扱わず理由を示して失敗させる。

重複DEMの採用順は、対応する標高基準、明示した品質・解像度・資料版、同順位の固定tie-breakで決める。ディレクトリ列挙順、絶対パス、ファイル更新時刻に依存させない。対応外のCRSや不整合な標高基準は診断し、無断で近似変換しない。

存在するチャンクだけを保存し、元解像度を超える詳細を作ったように扱わない。広域表示用の階層は必要な解像度だけを生成する。異解像度の境界で継ぎ目が出る条件を試験し、採用・補間規則を取り込み契約へ含める。

### 陰影と等高線

陰影はHorn方式の勾配、光源方位315度・高度45度・標高強調1倍を初期案とし、合成率とともにF0/F6で固定する。地理座標・Webメルカトル座標の差をそのままメートルとせず、緯度による地表距離を考慮する。式・補間・丸め・欠損近傍の処理を認定する。GDALの資料は近傍と単位の検証に使う参考仕様であり、GDAL実行ファイルへの依存を追加するものではない。[陰影の仕様参考](https://gdal.org/en/stable/programs/gdal_raster_hillshade.html)

タイルやDEMチャンクを越えた近傍サンプルを取得し、計算後に256pxへ切り出す。NoData周辺を0mとして黒い崖を作らず、未収録部には陰影・等高線を出さない。DEM収録外でも、収録済みの道路・建物・土地被覆は表示する。

等高線は取り込み時に本体内で生成し、完成DBへ保存する。初期案は20m刻みを基礎とし、100m・500m等の間引き表示と必要なLODを用意する。固定格子からセル単位で生成し、同値セル・平坦部・鞍点の接続、端点の座標、チャンク境界の所有規則を固定する。欠損や水面をまたぐ不要な線を作らない。XYZ要求ごとに独立生成しない。[DEMからの等高線生成の参考](https://gdal.org/en/stable/programs/gdal_contour.html)

### 合成描画

基本順は、海陸下地、土地被覆、陰影、水域・等高線、建物と交通地物の構造別描画とする。地下・地上・橋の例をF0の期待画像で固定し、橋が水面に埋もれないことを確認する。`layer`を全地物共通の絶対標高とは扱わない。

面単位で穴を持つ塗りを行い、穴を背景色で上塗りして下の地物を消さない。複数地物を一括した偶奇塗りで相互の重なりを穴にしない。タイル全体を覆う大きな面、タイル外に全頂点がある面、境界を跨ぐ穴も処理する。

描画順の最終比較キー、座標丸め、切り抜き、輪郭線・アンチエイリアスを固定する。道路が表示されないズーム0〜5でも、海陸・広域地表・地形は描画できる構造にする。

## 6. 識別と実行認定

既存道路の取り込み識別・描画契約v2・ID直列化は固定する。新形式には別の取り込み契約と、必要な項目を持つ描画契約v3を追加し、契約の版で判別する。既存契約の必須フィールド追加や全体版の一括置き換えは行わない。

| 新形式の識別 | 含めるもの |
| --- | --- |
| 入力一覧の識別 | PBF・DEM・陸域データの内容、役割、対象範囲、採用優先規則。複数ファイルは安定した順序で正規化 |
| 取り込み互換性とdataset ID | 入力一覧、対象タグ、面構築・欠損方針、CRS・標高基準、DEM格子・階層・量子化、等高線生成条件、LOD、schema/geometry版 |
| 描画契約とrender ID | 保存済みdataset ID、実際の形式、新スタイル値、可視条件、合成順、面描画、DEM階層選択・補間・陰影設定、等高線の表示、画像と実行系列 |

内容識別には保存先・日時・ソースコードのコメント・製品版・ビルド来歴を入れない。ZIPのコンテナ情報や入力一覧の並びの違いも、正規化した同じ入力内容・採用規則なら新形式の識別を変えない。入力資料のhashと正規化規則をメタデータへ保存し、取り込み中の入力差し替えも検出する。

ZIPでは展開後の対応XML内容のhashと資料の役割を安定順にまとめ、コンテナの作成日時や格納順を識別へ入れない。元ZIPのバイトhashは入力変更検査・来歴用に別保存する。GMLの任意の意味的同値まで自動判定することは初期要件にしない。

DEM・陸域データの実内容や取り込み規則を変えれば新dataset IDになる。色・陰影率など描画だけの変更では、元完成DBを再取り込みせず新render IDを作る。対応中の契約は保存済み契約から厳密に選び、未知の旧世代へ現在の描画を混ぜない。

`res/tile-render-execution.json`、`build_support/render_execution.rs`、互換性確認スクリプトを系列別の検証へ拡張する。新しいXML・ZIP・面演算等の依存も確認対象へ含める。依存追加時は道路の認定まで一律失効させず、旧35画像のdebug/release一致を確認した構成を追加認定する。未認定の系列は新規生成を止め、保存済みPNGの配信は維持する。

## 7. CLIの追加案

以下は**実装後を想定した案で、現時点では実行できない新オプションを含む**。F0で名称・入力形式を固定する。

```powershell
# 従来の道路取り込みは引数・既定動作を維持する。
& $exe local-tiles import --input 'D:/maps/japan.osm.pbf' --name '日本・道路'

# 建物・土地被覆・水域・陰影・等高線を持つ新しい完成DBを作る。
# elevation-input は対応するZIP/XML一式のあるディレクトリまたは入力一覧JSON。
& $exe local-tiles import --input 'D:/maps/japan.osm.pbf' `
  --name '日本・地物と地形' --features standard-v1 `
  --elevation-input 'E:/maps/dem/' `
  --landmask-input 'E:/maps/land-polygons/land_polygons.shp' `
  --invalid-areas skip-feature --json

# 取り込み結果のdataset IDを使い、契約・入力範囲・出典を確認する。
& $exe local-tiles datasets show --dataset $id --json
& $exe local-tiles datasets prepare --dataset $id --json

# render IDはprepareの結果から取得する。
& $exe local-tiles precompute plan --dataset $id --render $render `
  --bbox '139.6,35.5,139.9,35.8' --min-zoom 10 --max-zoom 15
& $exe local-tiles precompute run --dataset $id --render $render `
  --bbox '139.6,35.5,139.9,35.8' --min-zoom 10 --max-zoom 15
& $exe local-tiles background add --dataset $id --render $render
```

`--features`未指定と、過去の要求JSONでの項目欠落は`roads-v1`相当とする。`standard-v1`を明示したときだけ新形式にする。初期機能として地形の生成まで実装するが、DEM未指定や地域未収録の場合は利用可能な地物だけを描画し、入力・件数・有効範囲をCLIで確認できるようにする。

`--render`は既存の`url`に加え、事前生成・背景登録にも通す。未指定時の選択は形式別の既定契約で決定し、管理DBの列挙順に依存させない。履歴の再開は指定し直した既定値でなく、保存済みrender IDを使用する。

`datasets show`等へ分類別件数・面除外数・入力別資料版・DEM解像度・有効範囲・等高線条件・概算保存量を追加する。出典はOSMと国土地理院を既存の共通`attribution`へまとめ、255文字の制限とHTMLエスケープを守る。CLI用と背景登録用で別々の出典組み立てをしない。既存背景の既定値は自動変更しない。

出典は実際に採用した資料だけから集約する。DEM未指定の場合に国土地理院DEMを使用したと表示しない。

## 9. 受入条件

### 既存機能・識別

- 既存道路の固定35画像を上書きせず維持し、debug/releaseの画素・色解釈が一致する。新機能の固定画像は別に追加する。
- 一時環境の旧DB・PNG・履歴・manifestを使い、新旧同時登録、旧URLのhit/miss、背景登録、事前生成再開を確認する。旧完成DBのバイト列も不変。
- 過去JSONの欠落項目を道路取り込みと解釈し、request ID再送・過去ジョブ表示を維持する。
- コメント・整形・CLI文言・保存先・入力ファイル列挙順・ビルド来歴の変更で、該当しないIDが変わらない。内容・面構築・DEM選択・陰影等の実変更では必要なIDが変わる。
- 本体マイグレーションとタイル管理DBスキーマ1のSQL/checksumを維持し、共通フロントの比較に差分がない。

### 面・地形の正しさ

- 単純面、凹面、複数外周、中庭、島、逆向きmember、境界上の穴、タイルを完全に覆う面、日付変更線と世界端、不正面を検証する。
- 人工DEMの平面、一定勾配、山頂、谷、鞍点、0m、負標高、NoData穴、異解像度の重複を検証する。
- GMLの`startPoint`、軸順、末尾省略、1セルの位置ずれ、未対応CRS・標高基準の扱いを検証する。
- 個別256pxの4枚と、独立した512px描画を比較する。タイル境界とDEMチャンク境界を交差させ、欠損境界・面内部・穴も比較する。
- 道路・建物・海陸・陰影・等高線の候補列挙順を変えても結果が一致する。生成処理の失敗を空の成功PNGとして保存しない。
- 元PBF・DEM・海陸ファイルの削除・移設後も完成DBだけで描画でき、DEMだけを変更した新旧DBも混同せず同時利用できる。

### 容量・性能・停止

- 市街地、山地、湖沼、海岸の小領域で、抽出件数、staging/完成DB/journalピーク、DEM階層・等高線別サイズ、RSS、取り込み・miss描画時間を記録する。全国への容量倍率を測定前に断言しない。
- DEMは収録チャンクと必要階層に限り、全国1mの密配列や全ズーム複製を標準にしない。建物・等高線LODも共有・間引きを使う。
- 現在の道路の候補32MiB・1形状100万点等を安易に拡大せず、面のリング・頂点・クリップ後の辺数、DEMのチャンク・展開量・LRU、等高線の生成量にも上限を設ける。
- ZIP/XML解析・幾何処理・DEM階層・等高線生成・描画に取消と期限確認を入れる。空き容量不足・破損・取消・異常終了時にも、公開前の新ジョブ領域以外を変更しない。
- 大きなPBF/GMLでジョブ中に入力が変わった場合は完成公開しない。完成DBの検証後だけ成功として登録し、保存済みPNGや旧DBを整理対象へ自動追加しない。
- 検証出力を1か所へ集約し、debug情報・incrementalを抑制する。全国PBFの取り込みや全ズーム事前生成を自動試験に含めず、利用者の実DB・実データを試験対象にしない。

## 10. 導入・復帰の考え方

実装後は、利用者が入力PBF・DEM・陸域データを準備し、小地域の見積もりを確認して新形式を取り込む。通常アプリと書き込みCLIの単一所有者ルールは従来どおりとし、取り込みや切替のために既存ジョブを勝手に停止しない。

新完成DB・新世代を別登録し、狭い範囲の事前生成、出典・背景登録、共通地図での表示確認を行う。既存の道路背景は残し、初期の既定背景を自動変更しない。切替後も旧道路DBとPNGを保持するため、問題があれば背景を旧道路へ戻せる。新機能の削除・キャッシュ整理は別途明示的に行う。

新形式のDBを旧exeへ登録することはできないが、旧道路用の管理DBスキーマ・レコード・完成DB・PNGは維持する。旧exeへの復帰可能性を一時環境で検証し、手順書には対応できる契約と生成できる世代を明記する。

復帰対象は道路契約v2に対応する本調査基準相当のexeとする。旧道路背景への切替、新exeの正常終了、取り込み・事前生成ジョブと所有ロックの終了確認を済ませてから起動する。旧exeは残存activeジョブの復旧処理を行うため、実行中のまま入れ替えない。新形式の準備・取り込み再送・事前生成再開は旧exeで行わず、新URLのmiss生成も期待しない。復帰のために新DBや履歴を削除する必要はない。

現行の利用手順は[ローカル地図](../LOCAL_TILES.md)、これまでの実装は[描画世代識別の検証記録](LOCAL_TILE_RENDER_IDENTITY_PROGRESS.md)を参照する。本計画の新オプション・新形式・地形機能は、実装済みの機能として現行手順へ記載しない。
