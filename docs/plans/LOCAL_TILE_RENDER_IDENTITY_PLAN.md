# ローカル地図の描画世代識別の修正計画

作成日：2026-11-12。状態：R0〜R6の実装・自動回帰・隔離配布物作成済み。実アプリ・インストール確認は利用者が実施する。[実装・検証記録](LOCAL_TILE_RENDER_IDENTITY_PROGRESS.md)を参照。

調査基準はcommit `9c30ae1`。計画作成前の作業ツリーに未コミット変更はなかった。実装開始時は本計画と文書一覧の変更だけが未コミットで、それらを保持して進めた。利用者の設定JSON・DB・PNG・実行中プロセスには操作せず、ビルド・試験は隔離出力と一時データで行う。

## 1. 目的と設計上の判断

同じ完成DB・XYZ座標・描画互換性契約なら、コメント、整形、説明文、CLI、認証、進捗表示などを変更しても、描画世代・URL・PNG保存先を維持する。描画結果を変える変更を採用した場合に、該当する互換性版を更新して新しい世代にする。

推奨方式は、**明示的な互換性版、実際の描画設定値、描画回帰試験を組み合わせる方式**とする。全ソースのハッシュも、コメントを除いたソースのハッシュも、描画世代そのものには使用しない。後者でも、同等なリファクタリングや診断文の変更によって世代が変わるためである。

任意のコード変更がすべての入力で同じ画素を返すかを、ソース差分や有限の画像試験だけから自動判定することはできない。互換性版を更新する責務を明文化し、関係するコード・依存の変更をCIで検出して、変更内容の確認と画像比較を必須にする。

本計画でいう「描画結果」は、デコード後のRGBA、画像寸法、色空間、アルファの解釈を含む。PNGの圧縮率・圧縮手法だけが変わり、同じ画素と色解釈になる場合は世代を変えない。PNGのバイト列が異なり得ることと、表示結果が変わることを区別する。

## 2. 現状の問題

| 箇所 | 現在の識別入力・判定 | 影響 |
| --- | --- | --- |
| `build.rs`の`tile_build_id()` | 全`src/**/*.rs`のパスと生バイト、Cargo.toml、Cargo.lock、build.rs、target、最適化・debug設定、RUSTFLAGS、全feature、rustcの版 | コメント、CLI、本体API、製品版番号、描画に関係しない依存更新でもIDが変わる |
| `tilegen/dataset.rs`の`RenderProfile` | `renderer_version = roads-render-v1/<全体ビルドID>` | 完成DBが同じでもSDKの描画識別が変わる |
| 同`cache_key()` | dataset ID、保存された`importer_version`、取り込み規則、描画器、スタイル、画像契約、形式・寸法・XYZ | 描画器と取り込み元情報の両方からビルド来歴が入る |
| `local_tiles/service.rs`の`profile_record()` | 全体ビルドIDとSDKのz0キャッシュキーを再ハッシュ | ビルド来歴が二重に描画世代へ入る |
| service・jobs・CLI | `ProfileRecord.build_id == TILEGEN_BUILD_ID` | ID計算だけ直しても、準備済み判定・miss生成・事前生成が旧版扱いになる |
| `tilegen/import.rs` | PBFのSHA256・取り込み規則hash・全体ビルドIDからdataset IDを作成 | 描画以外の変更でも、同じPBFを新規取り込みすると別dataset IDになる |
| 同`importer_version` | 製品版番号と全体ビルドID | 診断情報が完成DB・SDKキーへ混入する |

`Style::hash()`は現在も色・線幅などの定数を含むが、可視条件や線幅計算の関数本体を自動追跡するものではない。単にビルドIDを削除し、現在のstyle hashだけを信頼する修正では、描画変更を見落とす。

## 3. 識別を三つに分離する

| 識別 | 役割 | 入力 | 使用しない入力 |
| --- | --- | --- | --- |
| ビルド来歴 | 不具合調査、生成元の確認 | 現行のソース・依存・コンパイラ・構成情報 | 描画可否・PNG世代・新規dataset IDの判断には使わない |
| 取り込み互換性 | 新規完成DBの内容を識別 | PBF内容、取り込み互換性版、欠損Node方針、抽出・属性・投影・LOD条件、schema/geometry版 | 製品版、コメント、CLI、現在の描画器の版 |
| 描画互換性 | 完成DBから得るタイル画像を識別 | 描画互換性版、実スタイル値、読取・座標・ラスタ化・画像解釈の契約、寸法 | ビルド来歴、保存パス、日時、ログ、待機数、worker数、期限 |

`TILEGEN_BUILD_ID`は診断用途として残せるが、描画・取り込みの互換性IDからの参照をなくす。PBF先頭検査の`HeaderProbe.build_id`も診断用途として維持する。

### 描画互換性契約

新規の`src/tilegen/identity.rs`等へ、取り込み・描画の互換性版と安定した識別計算を集約する。描画契約には次を明示する。

- 描画アルゴリズムの互換性版。順序、重なり、丸線、辺分割、丸め、アンチエイリアスの変更を管理する。
- 完成DBの読取・LOD選択・形状復号の互換性版。索引追加など、同じ結果になる最適化では据え置く。
- タイル境界・座標計算の互換性版、対象完成DBのschema/geometry版とその読取契約、タイル寸法。将来の対応可能な形式の一覧をhashへ入れず、新形式への対応追加だけで既存形式の世代を変えない。
- 色、線幅、可視条件などの実設定値と、その解釈規則の版。実装とhashの二重管理を減らすため、共通の宣言的な設定から描画と識別の両方を得る。
- RGBA、色空間、アルファ、PNGの色解釈を含む画像契約の版。
- 認定した数値演算・ラスタ化の互換性系列。描画依存の単なるpackage版番号とは区別する。

識別形式には版番号と用途別の接頭辞を置き、文字列長・整数・浮動小数点の表現を固定してハッシュ化する。ファイル配置、JSON整形、列挙順の偶然に依存させない。

概念上の計算は次のとおりとする。具体的な直列化形式はR0で固定する。

```text
import_identity = hash(取り込み互換性契約)
new_dataset_id  = hash(dataset-v2, source_sha256, import_identity, 取り込み条件)
render_identity = hash(描画互換性契約)
render_id       = hash(local-render-v2, 保存済みdataset_id, render_identity)
tile_cache_key  = hash(tile-v2, 保存済みdataset_id, render_identity, z, x, y)
```

SDKと本体で異なる描画入力を重複して管理せず、同じ`render_identity`を使う。既存完成DBに保存されたdataset IDはそのまま使い、新しい式で再計算しない。

### 変更時の判断基準

| 変更 | 世代の扱い |
| --- | --- |
| コメント・Rustdoc・改行・整形・同等の名前変更 | 維持 |
| CLI、認証、HTTPの管理処理、フロント、ログ、進捗、保存先、実行上限 | 維持 |
| 描画結果が同じリファクタリング、索引や問い合わせの最適化 | 互換性の確認後に維持 |
| 色・線幅・表示ズーム・描画順・形状処理・画素結果の変更 | 描画契約を更新し、新しいrender ID |
| PBF抽出・属性正規化・投影・LOD構築の変更 | 取り込み契約を更新。今後作る完成DBのIDへ反映し、既存完成DBの描画世代を一律に変えない |
| 同じ入力をデコードする処理も変わる投影・形状処理の変更 | 取り込み・描画の両方への影響を確認して該当契約を更新 |
| 色解釈を変えないPNG圧縮方式だけの変更 | デコード結果の一致を確認して維持 |
| PNGの色空間・アルファ等の解釈の変更 | 画像契約を更新し、新しいrender ID |
| 関係のない依存の更新 | 維持 |
| tiny-skia、libm、PNG関連依存、コンパイラ・CPU設定の変更 | 互換性を確認して維持、結果が変わる場合は該当契約を更新 |

正式な検証対象はWindows x64の配布構成とする。debug/releaseやコンパイラ版をそのまま世代へ入れず、同じ契約として認定する構成で画素比較を行う。未検証の浮動小数点最適化やCPU機能変更を、無条件に同じ世代で配布しない。

認定したtarget・コンパイラ・CPU機能・RUSTFLAGS・描画依存の構成は追跡ファイルへ記録し、ビルド時に実際の構成と照合した結果を実行コードへ渡す。未認定なら新規世代の準備・miss生成・事前生成を理由付きで拒否し、診断・既存PNGの読取は利用可能とする。この拒否は描画契約が古い場合の410と区別し、配信の新規生成では503と構成未認定の理由を返す。任意の環境変数で互換性判定を強制解除する仕組みは設けない。新しい構成の比較は一時データ専用の検証経路で行い、既存の公開PNGへ書き込まずに認定記録を更新できるようにする。

## 4. 取り込みと完成DB

新規取り込みでは、完成DBのdataset IDからビルド来歴を外す。`importer_version`には安定した取り込み互換性版を保存し、製品版番号・ビルド来歴は識別計算と別の診断情報へ置く。取り込み規則のhashは、実際の条件・対応形式を引き続き含む。

既存の完成DBは書き換えない。旧`importer_version`、dataset ID、登録IDをそのまま読み込み、描画に必要なschema・geometry・完成状態を検査する。日本の完成DBを再取り込み・再登録する必要はない。

SDKのキャッシュキーからも診断用の`importer_version`依存を外す。既存のIDが旧ビルド由来であっても、保存済みのデータ識別として固定して扱う。元PBFの再取得やDB全体の再ハッシュを、通常のURL照会・世代準備へ追加しない。

## 5. catalog・CLI・生成可否の判定

描画互換性を判定する共通処理を追加し、少なくとも次を切り替える。

- `service::profile_record()`、`datasets()`、`render()`のmiss時の判定と公開直前の再確認。
- `jobs::validate_precompute()`、計画、開始、再開時の世代確認。
- CLIの`current_profile_prepared`、`url`の省略時選択、互換性の表示。
- `datasets prepare`と`background add`の冪等な既存世代の利用。

catalog schema版1と`0001_catalog.sql`のchecksumは維持する。既存の`build_id`列は生成元の診断情報として保持し、新しいprofileの`info_json`へ`identity_version`、描画契約の構成と`render_identity`を保存する。準備済み・生成可能の判定には`build_id`を使わない。

同じdataset・描画契約なら、異なるビルド来歴でも同じprofileを使う。登録時の`ON CONFLICT ... DO NOTHING`は維持し、診断用の来歴が違うだけで既存profileを更新・増殖させない。

照会は新しいIDを計算・比較するだけで、profile追加、旧profileの再認定、完成DBの変更を行わない。照会で完成DBを開かなくても契約を判定できるよう、必要な構成はprofileに保存する。実際の生成前は完成DBのID・形式・現在状態を再検査する。

CLIの`current_build`は診断用ビルドの一致として保持し、保存されたprofileと現在の描画契約の互換性を表す`render_compatible`を追加する。実行構成の認定状況・新規生成不可の理由も診断で示し、契約互換性と実際の生成可否を混同しない。`build_id`と`current_build`が示すのはprofileの初回登録時の来歴であり、後から生成した個々のPNGの生成元を保証する情報ではない。実行中のビルド来歴は別の`app_build_id`で表示する。

`old_generation_cache_miss_status`もビルド一致ではなく描画互換性から決め、ビルド来歴が違うだけで410と案内しない。画面へ渡す通常の背景定義は変更しない。`src_frontend/`、`src/templates/`、PostgreSQL版のソースは変更しない。

## 6. 既存世代・PNG・履歴の切替

旧profileには、全体ビルドIDと、不透明なSDKキー、style/image版・寸法しか保存されていない。これらだけから、過去のプログラムと現在のプログラムが同じ画素を作るとは自動判定できない。

初回の新方式への切替は、次の安全策を採用する。

1. 旧dataset/profile ID、URL、PNG、manifest、ジョブ履歴、背景・共有を維持する。旧レコードやファイル名を新IDへ書き換えない。
2. 旧PNGのhit配信を維持する。生成互換性を証明できない旧世代のmissは、現在と同じ410とする。
3. 新方式は、利用者が`datasets prepare`を実行した時点で一度だけ新しい世代として準備し、必要に応じて`background add`で登録する。既存背景を自動置換しない。新URLは完成DBから必要なPNGを生成する。
4. 以後、同じ描画契約内のコメント・CLI・認証等の更新では、この新方式のID・URL・PNGを継続使用する。再度のprepare・背景登録は不要となる。
5. 既知の旧ビルドを同じ描画契約へ認定する対応表は初期実装に含めない。導入する場合は、過去の実装・依存・構成の根拠と検証を別途用意し、style版一致だけでは許可しない。

**識別方式の初回変更では一度だけ新URLを準備する計画であり、すべての旧PNGを新方式のURLからそのまま利用できるという計画ではない。** この方式変更と、今後のコメント編集による不要な世代変更を分ける。既存データの削除・再取り込みは発生させない。

事前生成manifestのversion 1と保存位置は維持する。新方式内では同じrender IDとなるため、コメント・アプリ側の変更後も中断済みジョブを同じmanifestから再開できる。互換性未確認の旧manifestを新世代へコピー・書換えして再開せず、条件不一致は理由付き409で拒否する。

退役、背景・共有からの参照保護、生成owner排他、取消、正常PNGの上書き禁止、終了時の実処理回収は維持する。

## 7. 検証と更新漏れの防止

### 描画回帰

合成PBFと小さな完成DBを使い、道路種別・全表示ズーム境界、リンク、橋・トンネル・層、重なり順、閉ループ、端部、急角度、継ぎ目、世界端、空タイルを固定する。RGBAを比較し、PNGもデコードして寸法・画素・色解釈を確認する。既存の投影bit列・閉ループLOD・丸線・境界の試験を継続する。

既存の実装から固定した基準画像を用意し、変更後の実装を使って期待値を自動再生成して合格させることはしない。基準更新は描画契約の更新理由と一緒に確認する。性能・取消・読取量の試験は画素互換性と別に維持する。

### 不要な世代変更の防止

- ビルド来歴、コメント・Rustdoc・整形、製品版、CLI・認証・ログ、描画と無関係な依存が変わっても、同じ完成DBのrender ID・SDKキーが変わらない。
- 同じ契約・入力条件の新規取り込みでは、ビルド来歴が違ってもdataset IDが一致する。取り込み契約・PBF・欠損Node方針の違いはIDへ反映する。
- 描画契約だけを変えた場合はdataset IDを保ち、render IDが変わる。
- 同じ描画契約で生成元build IDだけ違うprofileを使い、準備済み判定、URL出力、既存PNGの利用、miss生成、背景登録の冪等性、事前生成再開を検証する。`current_build=false`かつ`render_compatible=true`でも正常に使え、旧世代miss 410と誤表示しないことを確認する。
- 対応可能なDB形式を追加しても、既存形式を読む契約が同じなら、その既存DBのrender IDは変わらない。
- 未認定のcompiler・CPU機能・flags・依存構成では公開先への新規生成が拒否され、診断・既存PNGは利用できることを確認する。
- 未知の旧profileはPNG hitだけを返し、miss 410を維持する。照会による再認定やデータ変更がないことを検証する。
- 旧完成DB・catalog・PNG・manifest・履歴・共有の固定fixtureを使い、識別値と内容の保持を確認する。

### CIでの互換性判断

描画・読取・座標・スタイル・取り込みの対象ファイルと関連依存・featureを一覧化する。依存はCargoの解決済みグラフを使い、tiny-skia・libm・PNG等の直接依存だけでなく関連する推移的依存も確認する。変更検出に使う補助的なソース指紋は、Rustのトークン解析で通常コメント・Rustdocを除外する。正規表現によるコメント除去で、文字列やraw stringを壊さない。

この指紋はCIの確認対象を検出する用途に限定し、実行時の描画世代には入れない。対象の変更時は、契約版の更新か、据え置く理由・基準との差分検証を記録する。描画に関係する依存更新も同じ扱いとし、Cargo.lock全体の更新で自動的に世代を変えない。

CIの確認記録と画像試験は更新漏れを減らすものであり、全入力の同値証明ではない。未記録の変更、基準不在、未対応の識別形式を黙って互換として扱わない。

## 8. 実装段階と完了条件

| 段階 | 作業 | 完了条件 |
| --- | --- | --- |
| R0 契約固定 | 画素互換性の定義、取り込み・描画の構成、直列化形式、旧方式の扱い、認定構成と更新責務を固定 | 変更ごとの版更新基準、未認定構成の検出・停止方法、初回だけ新URLになる条件を文書から判断できる |
| R1 識別計算の分離 | `identity.rs`等、安定した契約・hash計算、ビルド来歴の診断化、Style設定の共通化、認定構成の検査 | 無関係な変更を識別入力から排除し、未認定構成から公開PNGを新規生成できない |
| R2 完成DB・SDK | 新規dataset IDとimporter版、SDK cache key・RenderProfileを切替 | 旧完成DBは非変更で読め、新規取り込みと描画の版を独立して更新できる |
| R3 実行管理・CLI | profile metadataと互換性判定を集約し、配信・照会・事前生成・背景登録へ適用 | 異なるビルド来歴でも同じ描画契約なら同世代として生成・再開できる |
| R4 旧世代と回帰 | 初回prepare、旧URL・PNG・manifest・参照保護、固定画像と識別の試験 | 旧情報を保持し、同じURLに異なる描画結果を混在させない |
| R5 CI・文書 | 関連差分の検出、互換性判断の記録、利用手順・SPEC・過去計画への追記 | 更新漏れを検知し、コメント更新での再登録案内が不要になる |
| R6 配布確認 | 全体回帰、共通フロント一致、同梱資材・exe・installerの確認 | 自動検証と利用者による実アプリ確認を分けて記録する |

実装時も実DB・実PNG・利用者の設定を操作しない。既存exe・distを上書きせず、利用者による切替まで稼働環境を維持する。

前回の容量増加を繰り返さないよう、検証出力は専用の1領域を再利用し、ビルド来歴の差の試験に本体全体の重複ビルドを用いない。必要な比較は小さな識別検証・合成データ・判定処理の試験で行う。検証用debug情報・incrementalの抑制はプロセス限定で設定し、配布exe・installer・必要な記録の退避先と出力容量を確認する。
